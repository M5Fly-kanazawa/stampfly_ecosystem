## 1. このドキュメントについて

### 背景 — なぜリセットしたか

旧 SIL は M1〜M11 と作り込むうちに、調査（特に M7）の過程で約4,500行＋多数のツールに膨張し、**開発者本人が進捗を追えなくなった**。原因は3つ：

1. **道具づくりと調査を一本の番号列に混ぜた** — 何が「SILという道具の完成」で、何が「その道具で旧機を調べた発見」か区別がつかなくなった。
2. **調査が枝分かれして膨張した** — 仮説が H1→H2→H3→H4 と二転三転し、人間が承認する節目が無いままAIが先行した。
3. **旧コードがAIを引っ張った** — 既存コードが文脈にあると、白紙から再設計せず既存を温存・延長する方向にバイアスする。

→ 旧 SIL を **git 履歴に残したまま全削除**し（4コミット、§11）、本書を起点に更地から作り直す。

### 対象読者

- vehicle_new の開発者（人間・AI）
- SIL で制御系・状態遷移・推定器を設計／検証する研究者・学生
- 自作の推定器・制御器を SIL で試したい学習者

## 2. SIL とは何か — 2つの核心原則

### 原則1: 物理ベースの「飛ばす前の検証」（実機データ不要）

SIL の主目的は、**まだ一度も飛んでいないファームを、ハードを壊さずに PC 上で検証する**こと。

- vehicle_new は未飛行＝**実機データは存在しない**。だから SIL が実機データを必要とする設計は目的と矛盾する。
- **真値（ground truth）は物理モデルから得る** — シミュレーションしているので、真の姿勢・位置・速度を常に知っている。実機ログを物差しにする必要はない。
- 旧 M7/M8（実機ログ再生・差分診断）の実機データ依存は **捨てる**。実機データの唯一の正当な用途は §3 の Model Fidelity（実機飛行後の後追い精度向上）だけ。

### 原則2: 算法非依存（実装でなくインターフェースに依存）

SIL は **「中身（ESKF という実装）」ではなく「継ぎ目（センサが入ってモータが出る接続点）」に依存する**。

- 未来のファームは ESKF とは限らない。推定器は相補フィルタ／Madgwick／フル EKF、制御は PID／状態フィードバック／MPC かもしれない。
- 継ぎ目は「ソフトの選択」でなく「物理」で決まるので**算法に依存しない**（IMU はどの推定器を使うか知らない／ESC はどの制御器が出した値か知らない）。
- **vehicle_new は既にこの設計**: `IEstimator`（`components/sf_estimator/include/estimator.hpp`）と `IController`（`components/sf_controller/include/controller.hpp`）の抽象インターフェースがあり、ESKF/PID はその一実装にすぎない。SIL はこのインターフェース経由で配線し、**ESKF の名前を一度も書かない**。

### 単一ハードが算法非依存を成立させる

stampfly は**ただ1機種**（固定センサ群 IMU/気圧/ToF/フロー、4モータ、固定の機体力学）だけを対象にする。ゆえに：

- 物理的に意味のある状態の**全集合**（位置・速度・姿勢・角速度・各バイアス…）が、**ファームと無関係に物理から確定**する。
- 真値を持つのは物理モデルで、常に完全。各推定器は「自分が計算した分だけ」を `estimate_state` に埋め、残りに「未推定」フラグを付ける。
- SIL は推定器の中身を知らず、**出された項目だけを物理真値と突き合わせ、出さない項目のゲートは適用しない**（例: 相補フィルタ＝姿勢のみ→位置ゲート不適用）。

> **要するに:** 入口（センサ）・出口（4モータ）・真値（物理）の3つは単一ハードで先に固定され、未知はアルゴリズムだけ。SIL は固定の3つにしか触らないので、中身を知らずにループが回る。

## 3. 開発フローのビジョン（SIL が回すループ）

SIL は単発の検証ではなく、**ハードを壊さずに回す開発ループ**の一工程である。

```
        ┌──────────────────────────────────────────────────┐
        │                                                  │
        ▼                                                  │
 [1] ファーム実装・変更（推定器/制御器/機能/パラメータ）          │
        │  ← 本体コードそのまま（Code Identity・Param Identity）  │
        ▼                                                  │
 [2] SIL検証（PC・物理シミュレーション・実機データ不要）           │
     物理モデル→合成センサ→ファーム本物ループ→モータ→物理（閉ループ） │
        │                                                  │
        ▼                                                  │
 [3] SIL検証 OK？                                            │
     ├─ NG → SILで原因を切り分け → [1]へ戻る（ハードを壊さず）────┘
     │  OK（合格ゲートを人間が承認＝ダッシュボード）
     ▼
 [4] 実機テスト（ハードに書き込んで飛ばす）
        ▼
 [5] 実機 OK？
     ├─ NG → 【差分診断】Code Identity だから切り分く
     │        ├ SILで再現する → ソフト要因 → [1]へ
     │        └ SILで再現しない → HW/タイミング/通信（SIL射程外）
     │                            or 物理モデルが甘い → Model Fidelity向上 → [2]
     │  OK
     ▼
 [6] 次の開発へ（次の機能・チューニング・次の学生課題）→ [1]
```

### 3原則（Code / Param / Model Identity）

| 原則 | 意味 | これが守られると |
|------|------|----------------|
| **Code Identity** | SIL は本体と同じソースをそのままコンパイルして走らせる（再実装しない） | 「SILで OK」が実機の振る舞いを意味する |
| **Param Identity** | 同じパラメータ（config）で走らせる | チューニングが SIL→実機 へ転移する |
| **Model Fidelity** | 物理モデルが現実とどれだけ合うか | 「SIL OK→実機 OK」がどれだけ成立するか |

### 実機データの唯一の居場所

実機データが正当に役立つのは **[5]→[2] の Model Fidelity 向上の一点だけ**。実機で飛んで初めて「物理モデルが現実とどれだけ合っているか」を測れる。これは**実機飛行が起きた後の後追いの精度向上**であって、**SIL の前提条件ではない**。

## 4. 合格ゲート — 「SIL検証OK」の定義

ゲート＝「これが通れば実機で飛ばしてよい」という、ハードを壊す前に PC 上で潰せる合否条件。すべて**物理モデルの真値**で機械判定でき、実機データは不要。

| ゲート | 確認内容（物理シミュレーション上で） | 観測量 |
|--------|-----------------------------------|--------|
| **G1 起動・状態遷移** | ARM→離陸→ホバ→着陸の遷移が正しく進むか。failsafe（通信断・低電圧・**衝突/衝撃**）が正しく作動するか | 状態列・アラート |
| **G2 推定の追従** | 推定器の出力が**物理の真値**にどれだけ一致するか（出された項目のみ、誤差が有界か） | \|推定−真値\| |
| **G3 閉ループ安定** | 制御込みで実際にホバするか。姿勢・位置が発散せず有界か | 姿勢/位置 RMS・有界性 |
| **G4 アクチュエータ健全性** | モータ指令が飽和・異常振動せず、リミット内か | duty・飽和率 |

各ゲートは **機械が合否＋根拠（数値・図）を出し、人間が承認**する二段（§8）。

## 5. アーキテクチャ

### 2層構造

```
┌──────────────────────────────────────────────────────────┐
│ ① SIL試験ベンチ（算法非依存・固定・これを作る）              │
│    物理エンジン(MuJoCo) → 合成センサ → センサトピック          │
│    actuator_motor トピック ← を読んで物理へ（閉ループ）        │
│    判定は境界観測量＋物理真値だけ。ESKFの名前を書かない         │
└──────────────┬───────────────────────────▲───────────────┘
      sensor topics                    actuator_motor
               ▼                             │
┌──────────────────────────────────────────────────────────┐
│ ② テスト対象ファーム（差替可能・中身は学生/開発者の自由）      │
│   [IEstimator: ESKF / Madgwick / 相補] → estimate_state    │
│        → [IController: PID / 状態FB / MPC] → mixer → motor  │
└──────────────────────────────────────────────────────────┘
```

①が継ぎ目（トピック／インターフェース）にだけ配線され、②が差し替え可能な中身。

### 深い継ぎ目 — ファーム本物のループをホストで走らせる

旧 SIL の失敗は、制御ループを再実装し、推定器を物理真値姿勢で回していたこと。新 SIL は**vehicle_new の実際の Pub-Sub ループ（`imu_task → estimate_state → control_task → actuator_motor`）を、ホスト上でそのまま走らせる**。推定器/制御器の差し替えは実機と同じ `IEstimator`/`IController` 経由。これが**ループレベルの Code Identity**。

### 状態モデル（階層・拡張性）

`estimate_state` は閉じた固定構造にせず、以下を**最初から実装**し、将来の未知状態のための拡張余地（予約フィールド／バージョニング）を残す。

| 層 | 状態 | 物理が真値を持つ / 推定器は |
|----|------|--------------------------|
| コア（固定） | 位置・速度・姿勢・角速度（剛体） | 常に生成 / 必須 |
| 共通 | ジャイロ・加速度バイアス | 生成 / 推定してよい |
| **環境（最初から）** | **外乱としての風** | 物理が初版から生成 / 推定してよい |
| **機体（最初から）** | **モータ健全度・劣化** | 物理が初版から模擬 / 検知してよい |
| 圏外 | 学習パラメータ等 | — / ファーム内部、SILは振る舞いで評価 |

→ **設計要件:** `estimate_state` の各項目に「これは推定していない」**valid フラグ**を持たせる（SIL がどのゲートを当てるか機械判定するため）。

## 6. 物理エンジン — MuJoCo

### 選定理由

8エンジンを比較した結果、**MuJoCo**（Google DeepMind, Apache-2.0）を採用。

- **ロボティクス標準**で検証済みの剛体＋接触力学。ドローン制御 SIL の実績多数。
- **ネイティブ C/C++ API**（`mjModel`/`mjData`/`mj_step`）。深い継ぎ目（ファーム本物ループを C++ で）と**同一プロセス・橋（C++↔Python）不要**。
- **決定論的**な固定ステップ（再現可能な SIL に必須）。headless（OpenGL不要）で軽量。
- **任意形状の衝突**（壁・地面・障害物）。

### 使い方 — センサ/モータは自作、内蔵モデルは検証リファレンス

制御・物理屋として、**モータ／センサのモデルは自分で書いて理解・所有する**。MuJoCo は剛体＋衝突の素体として使い、IMU/ToF/フロー/気圧の合成、モータ（推力・ラグ・健全度・故障）、風（外乱）は**自前で実装**する。

そのうえで、MuJoCo の**内蔵モデル**（`<accelerometer>`/`<gyro>`/`<rangefinder>`/`<motor>`）を**「自作実装を突き合わせる信頼できるリファレンス」**として使う。「自作で理解 → 内蔵と比較で納得」が一つのエンジンで完結する。

### ライセンス（Apache-2.0 を MIT プロジェクトで使う）

- Apache-2.0 は permissive で **MIT と自由に混在可**。プロジェクトは **MIT のまま**据え置き、copyleft でなく自コードの開示義務もない。
- 対応は2点だけ：① **MuJoCo を vendor（コピー）せず依存として取得**（CMake FetchContent / prebuilt lib）、② **`THIRD_PARTY_LICENSES` に Apache-2.0 全文＋著作権表示を同梱**。

### 衝突は第一級の検証要件

実飛行は壁衝突・墜落がある。SIL は剛体だけでなく**接触/衝突を再現**し、衝撃時の failsafe・状態遷移（G1）を検証する。

## 7. ホスト実行基盤（ファームを PC で走らせる）

### compat シム（新規に作り直す）

ESP-IDF / FreeRTOS の下回りを、コンパイルを通すための薄い差し替え（shim）で肩代わりする。**本体ソースは1行も書き換えない**。

| 対象 | PC での置き換え |
|------|----------------|
| FreeRTOS セマフォ | `std::mutex` |
| FreeRTOS キュー | `std::deque`（バイトコピー、満杯ドロップ再現） |
| `esp_timer` | シミュレーションのステップカウンタ（決定論のため壁時計を使わない） |
| `ESP_LOGx` | stderr（stdout の CSV を汚さない） |
| NVS（不揮発メモリ） | トピック実体をホスト側で提供 |

旧 compat は削除済み。深い継ぎ目（本物のタスクループ）を回すため、**タスク通知・タイマ駆動を含むより完全なホスト RTOS シム**を新規に設計する。

SIL を正しく繋ぐ作業が、そのまま以下を実装・検証して `@design` を `[OK]` にする作業になる。

## 8. sf CLI 統合・検証ダッシュボード

### コマンド体系（CLI 優先）

`sf sim`（飛行ビジュアライザ、workshop が使用）とは**別系統**として `sf sil` を新設する。

| コマンド | 役割 |
|---------|------|
| `sf sil build` | ホスト SIL をビルド（compat ＋ ファーム参照 ＋ MuJoCo） |
| `sf sil run` | SIL を実行 → `results.json` ＋ 図を生成 |
| `sf sil status` | 全ゲート G1〜G4 の合否を**機械算定**して表示（根拠の数値付き） |
| `sf sil review` | 人間の検証タッチポイント（図を見て承認） |
| `sf sil report` | `results.json` から単一ソースでレポート生成（コピペ廃止） |
| `sf sil gate <Gn> --approve` | 人間が承認 → 確定 |

### 機械判定＋人間承認の二段

- 各ゲートに**機械可読な judge 関数**（合格基準を数値で定義、例 `姿勢RMSE<2°`・`有界率>95%`）。
- SIL の生結果は `results.json`（**唯一の正**）。合否 ＝ `judge(results.json)` を機械が自動算定。図・数値・レポートはすべてこの単一ソースから生成（コピペでズレない）。
- 確定は必ず人間の `gate --approve`。AI が勝手に「合格」と先へ進めない。

### AI 対話ループの例

```
あなた「G2 は合格してる?」
  AI → sf sil status → results.json を読む
     → 「姿勢RMSE 1.5°（基準<2.0°）PASS、有界率 100% PASS。根拠の図はこれ→ 承認しますか?」
あなた「承認」
  AI → sf sil gate G2 --approve → 確定、次へ
```

### workshop 資産との共存

`sf sysid`・`sf sim`・`simulator/vpython`・`simulator/genesis`・教育資産は**アクティブな workshop が依存するため KEEP 厳守**。`sf sil` はこれらと独立した新系統として追加する。

## 10. 制約と非対象

### 守る制約

- **workshop KEEP厳守:** `sf sysid` / `sf sim` / `simulator/vpython` / `simulator/genesis` / `lib/stampfly_edu` / `examples/education`。
- **本体ソース不可侵:** ファームは一切書き換えず参照コンパイル（`git diff firmware/` が空を基準）。

### SIL の射程外（明示）

並行性（レースコンディション）・割込ジッタ・通信物理層は原理的に再現できない。SIL は決定論的な単一ループに潰しているため。**「SILが緑でも実機でタイミング起因の問題は出うる」**ことを常に意識する。切り分けられること自体を価値とする（§3 差分診断）。

- フラグした設計文書を新方針に**一貫リライト**: `firmware/vehicle_new/docs/{development_roadmap, noise_and_vibration_model}.md`（旧SIL前提の L1-L4 等の記述）、`control/validation/sil_control_validation.md`（旧SIL前提の検証レポート＝アーカイブ判断）。
