## 1. この文書について

### 背景 — なぜリセットしたか

旧 SIL は M1〜M11 と作り込むうちに、調査（特に M7）の途中で約4,500行＋多数のツールにふくれ上がり、**開発者本人が進捗を追えなくなりました**。原因は3つあります。

1. **道具づくりと調査を一本の番号列に混ぜてしまった** — 何が「SIL という道具の完成」で、何が「その道具で旧機を調べた結果」なのかが区別できなくなった。
2. **調査が枝分かれしてふくらんだ** — 仮説が H1→H2→H3→H4 と二転三転し、人間が立ち止まって承認する節目がないまま、AI だけが先へ進んでしまった。
3. **古いコードが AI を引っ張った** — 既存のコードが目の前にあると、白紙から設計し直すのではなく、それを温存・延長する方向に流れてしまう。

そこで旧 SIL を **git の履歴に残したまますべて削除し**（4コミット、§12）、この文書を起点に更地から作り直します。

### 想定する読者

- vehicle_new の開発者（人間・AI）
- SIL を使って制御系・状態遷移・推定器を設計／検証する研究者・学生
- 自分で書いた推定器・制御器を SIL で試したい学習者

## 2. SIL とは何か — 2つの基本方針

### 方針1: 物理シミュレーションで「飛ばす前に検証する」（実機データは不要）

SIL のいちばんの目的は、**まだ一度も飛んでいないファームを、ハードを壊さずに PC 上で検証する**ことです。

- vehicle_new はまだ飛んでいません。つまり**実機データは存在しません**。だから、SIL が実機データを必要とする設計は、目的と矛盾します。
- **真値（正解の状態）は物理モデルから得ます。** シミュレーションしている以上、真の姿勢・位置・速度は常に分かっているからです。実機ログを物差しにする必要はありません。
- 旧 M7／M8（実機ログの再生・差分診断）のように実機データに頼る作り方は**やめます**。実機データの正当な使い道は、§3 の Model Fidelity（実機で飛ばした後にモデルの精度を上げる、後追いの作業）だけです。

### 方針2: アルゴリズムの中身に依存しない（実装でなくインターフェースに依存する）

SIL は、**「中身（ESKF という具体的な実装）」ではなく「境界（センサが入ってモータが出る部分）」にだけ依存する**ように作ります。

- 未来のファームが ESKF とは限りません。推定器は相補フィルタや Madgwick かもしれず、制御は PID か状態フィードバックか MPC か分かりません。
- センサとモータの境界は「ソフトの選び方」ではなく「物理」で決まるので、**どんなアルゴリズムを中に入れても変わりません**（IMU は、あとでどの推定器を使うかを知りませんし、ESC は、その指令値がどの制御器から出たかを知りません）。
- **vehicle_new は、すでにこの形に設計されています。** `IEstimator`（`components/sf_estimator/include/estimator.hpp`）と `IController`（`components/sf_controller/include/controller.hpp`）という抽象インターフェースがあり、ESKF や PID はその一実装にすぎません。SIL はこのインターフェースを通して接続し、**ESKF という名前を一度も書きません**。

### 1機種専用だからアルゴリズム非依存が成り立つ

stampfly は**ただ1機種**（センサ群＝IMU・気圧・ToF・フロー、4モータ、機体力学がすべて固定）だけを対象にします。そのため、

- 物理的に意味のある状態の**全体**（位置・速度・姿勢・角速度・各バイアスなど）が、**ファームのコードとは無関係に、物理から先に決まります**。
- 真値を持つのは物理モデルで、これは常に完全です。各推定器は「自分が計算した分だけ」を `estimate_state` に書き込み、計算していない項目には「未推定」の印を付けます。
- SIL は推定器の中身を知りません。**ファームが出した項目だけを物理の真値と照らし合わせ、出していない項目は採点しません**（例: 相補フィルタは姿勢だけ→位置の採点はしない）。

> **まとめると:** 入口（センサ）・出口（4モータ）・真値（物理）の3つは1機種専用だから先に決まっていて、未知なのは真ん中のアルゴリズムだけ。SIL は決まっている3つにしか触れないので、中身を知らなくても動きます。

## 3. 開発の流れ（SIL が回すループ）

SIL は単発の検証ではなく、**ハードを壊さずに回す開発ループ**の中の一工程です。

```
        ┌──────────────────────────────────────────────────┐
        │                                                  │
        ▼                                                  │
 [1] ファーム実装・変更（推定器/制御器/機能/パラメータ）          │
        │  ← 本体コードそのまま（Code Identity・Param Identity）  │
        ▼                                                  │
 [2] SIL検証（PC・物理シミュレーション・実機データ不要）           │
     物理モデル→合成センサ→ファーム本物ループ→モータ→物理（閉ループ） │
        │                                                  │
        ▼                                                  │
 [3] SIL検証 OK？                                            │
     ├─ NG → SILで原因を切り分け → [1]へ戻る（ハードを壊さず）────┘
     │  OK（合格基準を人間が承認＝ダッシュボード）
     ▼
 [4] 実機テスト（ハードに書き込んで飛ばす）
        ▼
 [5] 実機 OK？
     ├─ NG → 【差分診断】本体と同じコードなので原因を切り分けられる
     │        ├ SILで再現する → ソフトが原因 → [1]へ
     │        └ SILで再現しない → ハード/タイミング/通信（SILで扱えない範囲）
     │                            または物理モデルが甘い → Model Fidelity向上 → [2]
     │  OK
     ▼
 [6] 次の開発へ（次の機能・チューニング・次の学生課題）→ [1]
```

### 3つの同一性（Code / Param / Model Identity）

| 同一性 | 意味 | これが守られると |
|--------|------|----------------|
| **Code Identity** | SIL は本体と同じソースをそのままコンパイルして走らせる（書き直さない） | 「SIL で OK」が実機の振る舞いを意味する |
| **Param Identity** | 同じパラメータ（config）で走らせる | チューニングが SIL→実機 へそのまま移る |
| **Model Fidelity** | 物理モデルが現実とどれだけ合っているか | 「SIL OK→実機 OK」がどれだけ成り立つか |

### 実機データの正しい使いどころ

実機データが役に立つのは、**[5]→[2] の Model Fidelity を上げる場面だけ**です。実機で飛ばして初めて「物理モデルが現実とどれだけ合っているか」を測れます。これは**実機で飛ばした後の、後追いの精度向上**であって、**SIL を作る・動かす前提ではありません**。

## 4. 合格基準 — 「SIL検証OK」とは何か

合格基準とは、「ここを通れば実機で飛ばしてよい」という、ハードを壊す前に PC 上で潰しておける条件です。すべて**物理モデルの真値**で機械的に判定でき、実機データはいりません。

| 基準 | 確認すること（物理シミュレーション上で） | 見る量 |
|------|--------------------------------------|--------|
| **G1 起動・状態遷移** | ARM→離陸→ホバー→着陸の遷移が正しく進むか。フェイルセーフ（通信断・低電圧・**衝突／衝撃**）が正しく働くか | 状態の並び・アラート |
| **G2 推定の追従** | 推定器の出力が**物理の真値**にどれだけ一致するか（出した項目だけ、誤差が有界か） | \|推定−真値\| |
| **G3 閉ループの安定** | 制御込みで実際にホバーするか。姿勢・位置が発散せず有界か | 姿勢/位置の RMS・有界性 |
| **G4 アクチュエータの健全性** | モータ指令が飽和・異常振動せず、リミット内に収まるか | duty・飽和率 |

各基準は、**機械が合否と根拠（数値・図）を出し、人間が承認する**2段階で確定します（§8）。

## 5. 全体構成

### 2層に分ける

```
┌──────────────────────────────────────────────────────────┐
│ ① SIL試験ベンチ（アルゴリズム非依存・固定・これを作る）        │
│    物理エンジン(MuJoCo) → 合成センサ → センサトピック          │
│    actuator_motor トピック ← を読んで物理へ（閉ループ）        │
│    採点は物理真値と「外から見える量」だけ。ESKFの名前を書かない  │
└──────────────┬───────────────────────────▲───────────────┘
      sensor topics                    actuator_motor
               ▼                             │
┌──────────────────────────────────────────────────────────┐
│ ② テスト対象ファーム（差し替え可能・中身は学生/開発者の自由）   │
│   [IEstimator: ESKF / Madgwick / 相補] → estimate_state    │
│        → [IController: PID / 状態FB / MPC] → mixer → motor  │
└──────────────────────────────────────────────────────────┘
```

①はトピック（インターフェース）にだけ接続され、②が差し替え可能な中身です。

### 接続は深いところで行う — ファーム本物のループをホストで走らせる

旧 SIL の失敗は、制御ループを自前で作り直し、推定器に物理の真値姿勢を渡して動かしていたことでした。新しい SIL は、**vehicle_new の実際の Pub-Sub ループ（`imu_task → estimate_state → control_task → actuator_motor`）を、そのままホスト上で走らせます**。推定器・制御器の差し替えは、実機とまったく同じ `IEstimator`／`IController` を経由します。これが**ループ全体での Code Identity** です。

### 状態の持ち方（階層的に・拡張できるように）

`estimate_state` は閉じた固定の構造にはせず、次を**最初から実装**し、さらに将来の未知の状態のための余地（予約フィールドやバージョン管理）を残します。

| 区分 | 状態 | 物理が真値を持つ / 推定器は |
|------|------|--------------------------|
| コア（固定） | 位置・速度・姿勢・角速度（剛体） | 常に生成 / 必須 |
| 共通 | ジャイロ・加速度バイアス | 生成 / 推定してよい |
| **外乱（最初から）** | **風** | 物理が初版から生成 / 推定してよい |
| **機体（最初から）** | **モータの健全度・劣化** | 物理が初版から再現 / 検知してよい |
| 対象外 | 学習パラメータなど | — / ファーム内部の話。SIL は外から見える振る舞いで評価 |

→ **設計上の要件:** `estimate_state` の各項目に「これは推定していない」という有効フラグ（valid フラグ）を持たせます。SIL が、どの項目を採点するかを機械的に判断するためです。

## 6. 物理エンジン — MuJoCo

### なぜ MuJoCo か

8つのエンジンを比較した結果、**MuJoCo**（Google DeepMind、Apache-2.0）を採用します。

- **ロボティクスの標準**で、検証された剛体＋接触の物理。ドローン制御の SIL に使われた実績が豊富。
- **ネイティブな C/C++ API**（`mjModel`／`mjData`／`mj_step`）。深いところでの接続（ファーム本物のループを C++ で動かす）と**同じプロセス内で完結し、C++↔Python の橋渡しがいらない**。
- **再現性がある**（同じ入力なら同じ結果）。固定ステップで、ヘッドレス（描画なし）で軽い。
- **任意の形状との衝突**（壁・地面・障害物）に対応。

### 使い方 — センサ・モータは自分で書き、内蔵モデルは答え合わせに使う

制御・物理が専門の立場として、**モータとセンサのモデルは自分で書いて理解し、納得して所有します**。MuJoCo は剛体＋衝突の計算の土台として使い、IMU・ToF・フロー・気圧の合成、モータ（推力・遅れ・健全度・故障）、風（外乱）は**自前で実装**します。

そのうえで、MuJoCo の**内蔵モデル**（`<accelerometer>`／`<gyro>`／`<rangefinder>`／`<motor>`）を、**自分の実装が正しいかを照らし合わせる、信頼できる答え合わせ**として使います。「自分で書いて理解する → 内蔵と比べて納得する」が、一つのエンジンの中で完結します。

### ライセンス（Apache-2.0 を MIT のプロジェクトで使う）

- Apache-2.0 は緩やかなライセンスで、**MIT と自由に組み合わせられます**。プロジェクトは **MIT のまま**で、コピーレフトではないので自分のコードを公開する義務もありません。
- やることは2つだけ。① **MuJoCo をコピーして取り込まず、依存ライブラリとして取得する**（CMake の FetchContent や配布バイナリ）。② **`THIRD_PARTY_LICENSES` に MuJoCo の Apache-2.0 全文と著作権表示を同梱する**。

### 衝突は最初から重要な検証項目

実際の飛行では壁にぶつかったり墜落したりします。SIL は剛体だけでなく**接触・衝突も再現**し、衝撃が起きたときのフェイルセーフや状態遷移（G1）を検証します。

## 7. ホストでファームを動かす基盤

### ESP-IDF 互換シム（新しく作り直す）

ESP-IDF／FreeRTOS の下回りを、コンパイルを通すための薄い代用品（shim）で肩代わりします。**本体のソースは1行も書き換えません**。

| 対象 | PC での代用 |
|------|-----------|
| FreeRTOS セマフォ | `std::mutex` |
| FreeRTOS キュー | `std::deque`（バイトコピー、満杯なら捨てる挙動も再現） |
| `esp_timer` | シミュレーションのステップ数（再現性のため壁時計は使わない） |
| `ESP_LOGx` | 標準エラー出力へ（標準出力の CSV を汚さない） |
| NVS（不揮発メモリ） | トピックの実体をホスト側で用意する |

旧シムは削除済みです。深いところで接続して本物のタスクループを回すため、**タスク通知やタイマ駆動まで含む、より完全なホスト用 RTOS シム**を新しく設計します。

### ファーム側で仕上げる未実装部分（P1 の前提作業）

SIL を正しく接続する作業は、そのまま次を実装・検証して `@design` を `[--]`（未検証）から `[OK]` にする作業になります。

| 箇所 | 現状 | やること |
|------|------|---------|
| `control_task.cpp:52-66` `applyMixer` | 未実装（全モータ0出力） | ミキサー（推力／トルク→4モータの duty）を実装する |
| `control_task.cpp:124` モータへの書き込み | 未実装 | 実機は LEDC、SIL は物理エンジンへ duty を渡す |
| 推定器・制御器の差し替え機構 | 具象型を直接 `static` 生成 | 実装を選べる仕組み（ファクトリ等）にする |
| `@design` タグ | すべて `[--]`（未検証） | SIL で検証して `[OK]` にする |

## 8. sf CLI への統合・検証ダッシュボード

### コマンド体系（まず CLI で作る）

`sf sim`（飛行のビジュアライザ。workshop が使用）とは**別系統**として、`sf sil` を新設します。

| コマンド | 役割 |
|---------|------|
| `sf sil build` | ホスト SIL をビルド（シム ＋ ファーム参照 ＋ MuJoCo） |
| `sf sil run` | SIL を実行し、`results.json` と図を生成する |
| `sf sil status` | G1〜G4 の合否を**機械が算定**して表示（根拠の数値つき） |
| `sf sil review` | 人間が確認する場（図を見て承認する） |
| `sf sil report` | `results.json` から一つの出どころでレポートを生成（手作業のコピペをなくす） |
| `sf sil video` | 飛行アニメと状態グラフを同期した、共有用の MP4 を生成（§9） |
| `sf sil gate <Gn> --approve` | 人間が承認して確定する |

### 機械の判定＋人間の承認、の2段階

- 各基準に**機械が読める判定関数**を持たせます（合格条件を数値で定義。例: `姿勢RMSE<2°`、`有界率>95%`）。
- SIL の生の結果は `results.json`（**この一つだけを正とする**）。合否は `判定関数(results.json)` を機械が自動で出します。図・数値・レポートはすべてこの一つの出どころから作るので、ズレません。
- 確定は必ず人間の `gate --approve`。AI が勝手に「合格」と判断して先へ進めないようにします。

### AI との対話の例

```
あなた「G2 は合格してる?」
  AI → sf sil status → results.json を読む
     → 「姿勢RMSE 1.5°（基準<2.0°）で合格、有界率 100% で合格。根拠の図はこれ→ 承認しますか?」
あなた「承認」
  AI → sf sil gate G2 --approve → 確定、次へ
```

### workshop の資産と共存させる

`sf sysid`・`sf sim`・`simulator/vpython`・`simulator/genesis`・教育用の資産は、**いま動いている workshop が使っているので必ず残します**。`sf sil` はこれらとは独立した新しい系統として追加します。

### フックで確実に実行する（手作業に頼らない）

各節目で動画とレポートを作るのは「義務」ですが、人の心がけに頼ると抜けます。**フックで自動化し、抜けない仕組みにします。**

- **`sf sil gate <Gn> --approve` は、成果物バンドル（`results.json` ＋ レビュー動画）が揃い、機械判定が合格していなければ承認を拒否します。** 成果物なしに先へ進めない、という構造にします。
- **git フック／CI**: 節目を示すコミットやタグ（例: タグ `sil-p1`）を打つと、`sf sil run` → `sf sil video` → バンドルの検証 を自動で実行し、揃わなければ止めます。
- これらは対応する `sf sil` コマンドができてから実装します（ゲートは P3、動画は P1 から）。それまでは手順として運用します。

### スキルとして1コマンドにまとめる

成果物バンドルを作る一連（SIL 実行 → 動画 → `results.json` → レポート → ゲート確認）は、**1つのスキル（例: `/sil-milestone`）にまとめます**。既存の `/lecture-video`（スライド→台本→動画を全自動）や `/commit` と同じ作り方です。

- 人間や AI は、節目で `/sil-milestone P1` のように一度呼ぶだけで、バンドル一式が揃います。
- フック（前項）は、このスキルを呼び出す／その成果物を検証する形で連動させます。**スキル＝作る手順、フック＝抜けを防ぐ仕組み**、と役割を分けます。
- `sf sil` コマンドが揃う P1〜P3 に合わせて実装します。

## 9. 共有用レビュー動画（YouTube／SNS）

### ねらい

SIL の検証結果を、そのまま**外部に見せられる動画**として書き出せるようにします。ecosystem を内外にアピールするうえで、かなり重要な機能です。**検証**（人間が飛行と状態を一目で理解する）と**広報**（魅力を伝える）を同時にこなします。

### 開発の各節目で必ず作る（義務）

ロードマップの各段（P1〜P4）を達成したとき、および主要な合格基準（G1〜G4）を通過したときは、**このレビュー動画を必ず作成します**。粗くてもかまいません（MuJoCo の描画で P1 から作れます）。

ねらいは2つ。**(1) 各節目に、人間が一目で確認できる成果物が必ず残る** — この計画の出発点だった「人間が確認・検証できるマイルストーン」を、そのまま形にします。**(2) ecosystem をアピールする素材が、開発が進むほど自然に貯まっていく。**

（`sf sil video` が動くようになったら、この義務を CLAUDE.md の必須ルールにも記載して、運用に乗せます。）

### 何を映すか

- **飛行のアニメーション（3D）**: シミュレーションした機体の動き。MuJoCo の描画機能を使い、まさに計算したとおりの飛行を映します（再現性があるので、何度作っても同じ動画になります）。
- **状態のグラフ（アニメと同期）**: 姿勢・位置・速度・モータ指令などを、アニメーションに合わせて流れる時系列グラフで描きます。推定値と真値の重ね描きや、合否（G1〜G4）の表示も入れられます。
- これらを並べて1本の MP4 に合成し、タイトルやラベルを付けて、SNS にそのまま載せられる品質にします。

### 使いどころ

- 「相補フィルタに差し替えても飛ぶ」というアルゴリズム非依存の実証（P2）を、そのまま動画にする。
- 旧と新の推定器の比較、パラメータを振った結果の比較。
- 壁にぶつかってフェイルセーフが働くデモ。

### 作り方

- 描画の土台は MuJoCo の描画機能を使います。物理の計算と描画の出どころが同じなので、**映像と計算結果が必ず一致**します。
- グラフは SIL の出力（`results.json` と時系列データ）から作り、各フレームを動画に合成します。
- `sf sil video`（§8）で一括生成。再現性があるので、同じ実行結果から同じ動画を何度でも作れます。
- workshop が使う既存のビジュアライザ（`simulator/genesis` の WebGL ビューアなど）とは別系統です。より凝った見栄えが必要になれば、将来そちらと連携する余地も残します。

### ロードマップ上の位置

- MuJoCo の描画は P1 から使えるので、**粗いアニメーションは早い段階から作れます**（早めにアピール素材を出せる）。
- SNS 向けの仕上げ（合成・タイトル・比較レイアウトの自動化）は **P4** として独立させます。

## 13. SIL 検証能力の充実（P5〜P10）

> 2026-06-01 追加・ユーザー承認済み。P1〜P4 を達成した時点で、SIL が**実機コードをどこまで検証できるか**を充実させ、その充実度を計測する章。

### 背景と狙い

P1〜P4 は**理想 SIL**（クリーンなセンサ・無風・健全なモータ）で、閉ループホバー・アルゴリズム非依存・CLI ダッシュボード・比較動画を達成した。一方、現実の検証に必要な**ノイズ・外乱・全飛行モード・衝突/フェイルセーフ**は未実装で、`@design` タグはほぼ `[--]`（未検証）のまま。本章はそれらを SIL に入れて実機コードの検証網羅性を高め、最後に「何をどこまで検証したか」を計測する。

### 共通原則

- **決定論を保つ**: ノイズ・外乱はすべて**シード付き乱数**（`std::mt19937`、シードは Config）で生成する。同じシード→同じ実行→同じ動画（再現性）。比較（ESKF vs 相補）は両者を**同一シード**で走らせ、ノイズ実現値を一致させて公平に比べる。
- **本体は原則無改変、ただし last-mile を伴う段がある**: P8（ACRO/POS_HOLD の制御則は実装済みだが SIL 未検証）と P9（衝突検出は本体に未実装＝新規実装）は、ミキサー last-mile と同じく「本体を実装して SIL で `[OK]` にする」作業を含む。
- **各段はアウトプット主導**: results.json＋レビュー動画＋ゲート承認のバンドル（§8〜§10）。段ごとに人間の確認節目を挟む（段階的、旧 SIL の教訓）。

### P5 — センサノイズ N0（白色ガウス＋バイアス）

- **実装**: Plant に `NoiseConfig`（IMU ノイズ密度・起動バイアス・バイアス RW 密度・シード・enable）を追加。Plant が RNG とバイアス状態を持ち、`imu()` に per-sample ガウスノイズ＋バイアスを載せ、`step()` でバイアスのランダムウォークを進める。離散ノイズ σ_d = σ_c/√dt（σ_c=ノイズ密度 [unit/√Hz]）。仕様は `firmware/vehicle_new/docs/noise_and_vibration_model.md` §2-3。
- **テスト（ユニット）**: ①測定 σ ≈ 設定 σ（統計）②固定シードで完全再現（同シード→同列、異シード→別列）③enable=false で従来のクリーン経路と完全一致 ④バイアス RW が √t で成長。
- **ゲート**: G2（ノイズ下で ESKF・相補とも姿勢推定 RMSE が閾値内・有界）＋既存 G3（ホバー維持）。起動バイアスにより**ESKF（BG/BA を推定）が相補（バイアス非推定）より追従が良い**差が出始める。
- **成果物**: ノイズ下ホバー動画＋results（noise メトリクス・G2 チェック）。
- **✅達成（2026-06-03）**: ノイズモデルは `plant/sensor_noise.hpp` に実装済みだったが、エミュレータ（`emu_vehicle`/`emu_vehicle_new`）は既定 Config（noise off）で `Plant::init` を呼んでおりノイズを有効化する経路が無かった。`SIL_EMU_NOISE=n0`/`SIL_EMU_SEED` env を両 emu 入口に配線し、`sf sil scenario --noise n0 --seed N` から制御できるようにした（既定 off は従来と byte-identical＝クリーン経路不変）。検証:
  - **G2（有界）**: `hover_alt`（16s保持）を 7 シードで実行し全て有界（保持窓 alt 帯 ~0.13m、std 1.3–3.9cm）。`hover_long`（90s保持）で長期も alt std~2.7cm・緩い有界ドリフト（−35mm/75s）、姿勢チルト平均~4°（max 10°）で発散なし。
  - **決定論**: 同シードで trajectory・stdout・stderr が完全一致（byte-identical）。異シードは別実現。
  - **白色σの substep 非依存化（時間基準修正の副作用を是正）**: 物理は 4kHz substep で `advance()` するが、ファームは IMU を 400Hz で読む。白色を substep（0.25ms）で離散化すると σ が √10 倍に膨らむため、`SensorNoise::Config::white_dt`（=400Hz 読み取り周期）で白色を離散化するよう分離。`noise_test` に substep 分離テストを追加して数値確認（4kHz substep でもファームが見る σ は 400Hz 相当）。バイアス RW は √dt 累積ゆえ substep のままで正しい。
  - **レビュー動画**: `viz/out_scn_hover_alt/scn_hover_alt.mp4`。`render_video.py` 単一 run のカメラを毎フレーム px/py 追従（chase）に修正し、床プレーンを 3m→200m に拡大（物理は不変＝プレーン衝突は無限）。
- **知見（→P6 の動機）**: ALTITUDE_HOLD は高度＋姿勢のみ保持し**水平位置を保持しない**ため、N0 の残留 accel バイアスが ESKF 姿勢に~4°のチルトを生み、その積分で機体が水平に数十m ドリフトする（高度・姿勢は有界＝G2 は満たす）。これは `sensor_noise.hpp` が記す ESKF accel-bias 感度（biasが姿勢を傾ける）の顕在化で、**P6 で起動校正（水平静止 ba_z≈2g）を再現**し残留バイアスを抑えるべき動機になる。なお `hover_long` の着地で 12m まで上昇するのは、ノイズで姿勢が乱れた接地で衝撃検出→crash DISARM 後に起きる MuJoCo 剛体接触の数値爆発（モータは disarm 済み）で、P5 のホバー/ノイズ欠陥ではない（接触剛性の軟化は別タスク）。

### P6 — センサノイズ N1/N2（スロットル依存・帯域制限）＋ ToF/Baro/Flow

- **実装**: スロットル依存の振動（軸別 K、σ_axis = K[axis]·duty²）＋帯域制限（f_low/f_high）。ToF/Baro/Flow にも観測ノイズ（R 表）。同 doc §3-4。
- **ゲート**: G2 強化＝**ノイズ下で ESKF 優位を定量化**（P4 比較動画をノイズ版に更新し「中身が違うと結果も違う」を見せる）＋G4（飽和率）。
- **成果物**: ノイズ下 ESKF vs 相補 比較動画（P4 を意味あるものに）。
- **進捗（2026-06-03）— N1 実装済み（段階1/3）**: スロットル依存振動 σ_axis=K[axis]·duty² を `sensor_noise.hpp` に追加（軸別 K=accel{3.96,2.35,5.64}/gyro{1.08,0.83,0.15}、Plant が4モータ平均 duty を substep 毎に供給）。`SIL_EMU_NOISE=n1` で有効化（n0=静的のみ）。`noise_test` に軸別 σ 検証＋ゼロスロットルで消失を追加。N0/off は byte-identical（不変）、n1 は同シードで決定論。**所見**: N1（広帯域振動）下では hover_alt の離陸が揚力不足になり機体が沈下（有界・非発散だが品質劣化）。これは広帯域ゆえ低周波成分がファーム LPF を通過し ESKF を実機以上に劣化させるため＝**N2 帯域制限の動機**（doc §4「LPF の必要性理解」）。なお SIL の hover duty(~0.62-0.70)は legacy hover02 のフィット点より高く、K·duty² で振動がやや過大に出る点は留意。**残（段階2/3）**: N2＝振動の帯域制限（500-667Hz を物理 4kHz substep で生成し 400Hz 読みでエイリアシング＝白色とは別経路）＋ToF/Baro 観測ノイズ R。**残（段階3/3）**: ESKF vs 相補の比較（要ハーネス判断＝emu_vehicle_new の IEstimator 切替 or 既存 hover_smoke 比較経路）。

### P9 — 衝突・閉室・フェイルセーフ

- **実装**: MJCF に壁・天井（閉じた部屋）を追加（MuJoCo が衝突計算）。**本体に衝突検出を新規実装**: IMU 比力の大きなスパイク（閾値）で衝撃を検知→状態機械を EMERGENCY へ→**全モータ停止**。検出は実機と同じ原理（専用接触センサ無し）。
- **ゲート**: G1（衝突後に状態遷移・フェイルセーフ＝モータ停止が正しい順で流れる）。
- **成果物**: 衝突→モータ停止のフェイルセーフ動画（§9 活用例）。

### P10 — 検証カバレッジ計測

「SIL が実機コードをどこまで検証したか」を測る。
- **① `@design` タグ網羅（主）**: コード内の `@design ... [--]/[OK]` を集計し、SIL シナリオで `[OK]` 化した割合を出す（SIL 本来の仕事＝§7）。
- **② シナリオ×要件マトリクス（主）**: 縦＝本体が満たすべき要件（各モード・各フェイルセーフ・各状態遷移）、横＝SIL シナリオ（P5〜P9）。交点に「励起した」印。空行＝未検証の抜け。
- **③ コードカバレッジ（任意補助）**: ホストビルドに gcov/llvm-cov を有効化し、本体ソースの行・分岐カバレッジを自動計測。①②が見落とす「どのシナリオでも一度も走らない関数」を拾う安全網。
- **ゲート**: `sf sil coverage` がレポート（results.json＋表）を出し、人間がレビュー。①②は意味的網羅（正しいものを検証したか）、③は機械的網羅（どの行が走ったか）。

### この章での `@design` タグの扱い

各段で検証した本体の設計要素は `@design ... [--]` を `[OK]` に更新する（P10 ①の母数）。リリース時に全 `[OK]` を目指す（CLAUDE.md vehicle_new ルール）。
