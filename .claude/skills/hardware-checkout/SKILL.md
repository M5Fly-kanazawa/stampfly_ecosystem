# `/hardware-checkout` — 実機確認の進行役

基準となる文書は `firmware/vehicle/docs/hardware_checkout.md`（以下「手順書」）。このスキルは手順書の内容を
変えない。**手順・合格線・中止条件は必ず手順書から読み、記憶や推測で補わない。** 手順書とこのスキルが
食い違ったら手順書に従い、食い違いを利用者に伝える。

## 1. 役割分担（最優先の規則）

実機確認は**開発者 1 人と Claude Code**で行う（2026-11-22 の決定。2 人目はいない）。**モータを止める手段は人だけが持つ。**
Claude Code の応答は数秒遅れうるので、緊急停止は Claude Code に任せない。

| 誰が | すること |
|------|----------|
| Claude Code が実行する | 次の手順の提示、入場条件・人数の確認、USB コンソールへの入力（モータが回る `motor test` を含む）、CLI の `arm`・`disarm`・`mode`（USB・WiFi。開発者の承認済み）、WiFi の取得（`sf log wifi`）と WiFi の CLI（`nc 192.168.10.1 23`）、飛行の命令（`sf takeoff`・`sf cw` など）の送信、保存済みの記録の読み取り（`sf log info`・`sf log stats`・`sf log check`・`sf log viz --save`）、合格線との照合、進行記録の更新、`git`・`sf doctor`・`sf build vehicle` |
| 人（開発者）が行う | 機体・送信機・電池・プロペラ・重りや固定具に触れる全ての操作（送信機の ARM・DISARM を含む）。飛行の間は送信機を持ち、DISARM の用意をする。1g は片手で機体、片手で送信機を持つ |
| **緊急停止は人** | 送信機のスロットル側スティックの押し込み、機体のボタン、電池を外す。Claude Code は `emergency`（CLI の命令、`sf emergency`）を頼まれたときに送るが、止める手段に数えない |
| 利用者の承諾を得て Claude Code | `sf flash vehicle`（手順 0-5。その都度「書き込んでよいか」を聞く） |

- 手順書 1 章の人員の表が、手順ごとの分担と 1 人での可否を決める。**2-5・2-7・2-8 は 2 人目がいないと行わない**
  （2-7・2-8 は、通信途絶の模擬が入るまで 1 人では行わない）。1h-2・1h-3 は電源装置が要る任意の手順で、
  1 人で行うかは責任者の判断（行わなければ「未実施」）。
- モータが回りうる命令（`motor test`、`arm`）と飛行の命令は、送る前に何が起きるかを利用者に伝える。
  **伝え方は音声（macOS の `say`）を使い、文字だけにしない**（手は機体・送信機にふさがり、画面を見ていない）。
- 飛行中は指示を出さない。飛行の前に「この飛行の目的・操作の順・中止の段」を全部伝え、利用者の合図を受けて
  命令を送り、着陸とモータ停止の報告を受けてから次へ進む。

### 音声の合図の言い方

人に操作を促す合図は、次を守る（2026-11-22 の失敗: 「切り替え」と言っても、何を押すのか伝わらなかった）。

- **何を押すかを言う**（例: 「右ボタンを押す」「スロットル側スティックを押し込む」）。「切り替え」「操作」だけで済ませない。
- **回数を付ける**（例: 「右ボタンを 10 回」）。
- **回の頭で数える**（例: 「1 回目、押す」）。回の途中で数えない。
- 1 つの合図に 1 つの操作だけを入れる。

## 2. 始めるとき

1. `logs/checkout/progress.md`（進行記録。Git の管理外）があれば読み、続きの位置を利用者に伝える。無ければ作る。
2. 手順書の 1 章（進行の一覧・人員と端末・操作の対応）、2 章（安全上の規則）、3 章（使い方）を読む。
   その後、これから行う段階の章だけを読む（先の段階は、入るときに読む）。
3. `git status --short` と `git log -1 --format=%H` で、試験するコミットを確かめて進行記録に書く。
   `firmware/` か `lib/sfcli/` に差分があれば止めて利用者に知らせる。
4. 利用者に次を聞く（1 回にまとめる）: 今日行う範囲、操縦者と責任者は誰か、今いる人数、電池の本数、
   下の「3. ネットワーク」のどちらで進めるか。
5. 手順書 2 章の共通の規則と「中止の段」を要約して示し、読んだことの確認をもらう。飛行の日は毎回行う。

## 3. ネットワーク（機体の WiFi とインターネット）

機体の WiFi（SoftAP、192.168.10.1）にはインターネットが無い。Claude Code はインターネットが要る。
PC が機体の WiFi だけにつながっている間、Claude Code は応答できない。始めるときにどちらかを選ぶ。

| 方式 | 内容 |
|------|------|
| A 同時接続 | PC を有線 LAN または USB テザリングでインターネットにつなぎ、WiFi は機体につなぐ。**2026-11-22 に実機で両方が同時に通った**。最初に、機体の WiFi につないだ状態で `sf log wifi -d 5 --no-save` が通ることを確かめる |
| B 区切って進める | 機体の WiFi につなぐ前に、その区切り（手順 1 つ、または飛行 1 回）の操作・コマンド・中止条件を全部示す。利用者は手順書を開いたまま実施し、記録を保存して、インターネットに戻ってから報告する。Claude Code は保存された一式を読んで照合する |

USB だけで済む手順（段階 0 の大部分、1a、1d など）は、どちらの方式でも通常どおり対話で進められる。

**macOS で Python の通信が拒否されるとき**: 端末アプリからの Python のローカルネットワーク通信が拒否されることがあり、そのとき `sf log wifi` は `No data received` になる。
見分け方: `nc -z 192.168.10.1 23` は通る（Apple 製のコマンドは通る）のに、`sf log wifi -d 5 --no-save` が届かない。
対処: システム設定の「ローカルネットワーク」で、使っている端末アプリを許可する。別の対処として、UDP の中継を使った実績がある。
どちらでも通らないときは、止めて利用者に知らせる（機体側の不具合とは限らない）。

## 4. 1 手順の進め方

手順書の表の 1 行（例: 0-7、1b、2-3）ごとに、次の順で進める。章を丸ごと貼らない。

1. **提示**: 手順の番号と目的、必要な人数（1 章の表）、固定の状態（段階 0・1）、打つコマンド（端末 T1・T2・T3 の別）、
   記録するもの、合格線、その手順の中止条件。人数が足りない手順は始めない。
2. **待つ**: 利用者の報告（表示された値、保存したファイル名、目で見たこと）を待つ。
3. **照合**: 保存された一式があれば、手順書が指定する `sf log stats` のモードと `sf log info` を実行して値を読む。
   合格線と比べ、合格・不合格・判定できない、のどれかを理由つきで伝える。「暫定」と書かれた線は暫定と伝える。
4. **記録**: 進行記録に 1 行足す（下の書式）。
5. **次へ**: 合格なら次の手順。不合格なら止めて、手順書の指示（中止、やり直し、責任者の判断）を示す。

守ること:

- 合格線を緩めない。値が線をわずかに超えたときも不合格と記録し、責任者の判断を仰ぐ（規則 11）。
- 手順書が「未確認」と書いた事項は、実機で分かった事実をそのまま記録する。推測で埋めない。
- 段階の入場条件（前の段階が全て合格、段階 2 の入場の表）を満たさないまま次の段階へ進めない。
  責任者が進むと決めたときは、その判断と理由を進行記録に書いてから進む。
- **段階 0・1 は、プロペラを付けたまま、機体を固定して行う（開発者の決定、2026-11-22）。** 手順書 0-1 の「固定の条件」
  （重りまたはベンチ台、動かない・視野をふさがない・回転面に触れない・水平・机の端から落ちない）を確かめる。
  段階 0・1 の各手順の提示で、固定が保たれていること（重り・ケーブルの位置を含む）を確かめる。1g は機体を手で持つので、
  そのときだけ固定を外し、プロペラは付けたままで、指を回転面に入れない。機体が動いた、重りや固定具がずれた、固定具や
  ケーブルがプロペラに触れたら、すぐ DISARM して電池を外し、固定をやり直す。段階 2 の入場では、プロペラの取付の向き
  （時計回り用・反時計回り用）と緩み、重り・固定具を外したことを確かめる。
- この手順は StampFly の大きさを前提にしている。大型の機体には当てはめない。
- 飛行の手順では、提示のたびに「中止の段」のどれがこの飛行に当たるかを示す。
- 飛行後は毎回、手順書 3 章の「飛行後の共通の確認」（C1・C2・C15・電池・構造）を行う。
- 予定外の再起動、有限でない値の検出、`period max` 10 ms 以上などの全段階の中止条件に当たったら、
  その日の飛行を止め、記録を保存して原因の調査に切り替える。

## 5. 記録

| ファイル | 内容 |
|----------|------|
| `logs/checkout/progress.md` | 進行記録。日付、試験するコミット、操縦者・責任者、方式 A/B、固定の方法と重りの重さ（手順 0-1）、手順ごとの行 |
| `logs/checkout/results.md` | 手順書 8 章の結果表を写して埋めたもの。段階の終わりごとに更新する |
| `logs/checkout/*.sflog.zip`、`console_*.txt` | 利用者が保存する取得の一式とコンソールの記録（名前の規則は手順書 3 章） |

進行記録の 1 行の書式:

```
| 日時 | 手順 | 確認項目 ID | 記録（値・ファイル名） | 判定 | 備考 |
```

`logs/` は Git の管理外なので、これらはコミットされない。段階 4（取りまとめ）で、結果表をどこに残すかを
利用者に聞く。**コミットと push は、利用者が頼んだときだけ行う。** リポジトリ直下の `flip_test2.sflog.zip` が
あっても触れない。

## 6. 実機確認の間にしないこと

- ファームウェア・sf CLI のソースを変えない。不具合を見つけたら、記録して利用者に報告し、直すかどうかは
  利用者が決める。ソースを変えた場合は試験するコミットが変わるので、手順 0-2 からやり直す。
- 制御パラメータを、手順書の「変更するパラメータ」の表にあるもの以外は変えさせない。
- 手順書の合格線・中止線・手順を、その場で書き換えない。直すべき点は進行記録の備考に集め、段階の終わりに
  まとめて利用者に示す。

## 7. 後の判断のために必ず残す値

次の値は、実機確認の後に利用者が設計の判断に使う。毎回、数値で進行記録に残す。

| 値 | どこから読むか | 何の判断に使うか |
|----|----------------|------------------|
| 有限でない値の検出数（`finite` 行、`nonfinite`） | `status`、`sf log stats loop` | 検出時にモータを止める機能を入れるかどうか |
| 気圧高度と ToF の差、学習したオフセット | `sf log stats baro` | 気圧を ToF なしの降下に使うかどうか |
| 低いホバーでの ToF の 1 秒の幅 | `sf log stats spread` | 接地判定の静止の帯（2 cm）が実機に合うか |
| 着陸開始からモータ停止までの時間と、働いた判定経路 | `sf log stats events`、`sf log info --text` | 接地判定の保持時間（1 秒）が実機に合うか |
| 回頭中の ToF の高さの最小と水平位置のずれ | `sf log stats turn` | 回頭の速度の上限が実機に合うか |
| ARM 中の `period max`・`busy max`（WiFi の取得の有無で比較） | `sf log stats loop` | ログの WiFi 送出が 400 Hz の周期に影響するか |
