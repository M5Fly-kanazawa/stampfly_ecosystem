状態: **見直し中**（Phase 0〜3 完了。Phase 4 実機検証の初回は 2026-10-02 に失敗: 機体が反転して真下へ墜落。`flip.enable`（既定 0）で FLIP を既定無効にした。原因解析の結果、構造側の欠陥（Brake が終わらない等）は §10 のとおり修正済み。レートプロファイルは §5.7 のとおり「計画 360° プロファイル」に作り直し、実機に合わせた SILS プラントで数値的に裏付けた。実機での再試験（§11）は未実施）。

## 3. 提案アルゴリズム（案 A: 角度スケジュール型）

### 3.1 実行条件

以下をすべて満たすときだけ開始する。満たさないときは API へ `error flip: <理由>` を返し、機体は何もしない。

| # | 条件 | 暫定値 | 理由 |
|---|------|--------|------|
| C1 | `FlightState::FLYING`（TAKEOFF/LANDING 中は不可） | — | 規範表（§4.3） |
| C2 | 対地高度 h ≥ h_min | 1.0 m（§5.3） | 高度損失の余裕 0.5 m + ToF 再取り込みの余裕。天井余裕は開始高度 + 0.6 m 以上（最大上昇 20〜30 cm + 余裕） |
| C3 | 姿勢 \|roll\|, \|pitch\| ≤ 15°、角速度 \|ω\| ≤ 60 °/s | — | 回転角の積算を 0 から始める |
| C4 | 速度 \|v_h\| ≤ 0.3 m/s、\|v_z\| ≤ 0.2 m/s | — | 回復後の位置制御の復帰を容易にする |
| C5 | 電池電圧 ≥ V_min（負荷時） | 3.6 V（シミュレーションと実機ログで確定） | 減速・回復に推力とトルクの余裕が要る |
| C6 | 推定器が正常、ToF が有効（高度の観測が生きている） | — | h_min の判定根拠 |
| C7 | 前回の Flip 終了から t_gap 以上 | 2 s | 推定器の再収束・電池の回復 |
| C8 | 同定励振・オートチューン・誘導移動（`cmdMove`/`cmdRotate`）が実行中でない | — | 設定点の出所が二重にならないようにする |

天井までの距離は機体に上向きセンサが無いため判定できない。**開始高度 + 0.5 m 以上の天井余裕は操縦者の責任**とし、操作手引きに明記する。

### 3.2 フェーズ

回転軸の単位ベクトル e_f（機体座標 FRD）と符号 s を方向から決める:

| 方向 | 軸 | レート指令の符号 | 備考 |
|------|----|-----------------|------|
| `r` | x（ロール） | p_cmd = +ω_flip | 右翼下げ方向 |
| `l` | x（ロール） | p_cmd = −ω_flip | |
| `b` | y（ピッチ） | q_cmd = +ω_flip | 機首上げから後方へ |
| `f` | y（ピッチ） | q_cmd = −ω_flip | 機首下げから前方へ |

回転角 φ は開始時刻からのジャイロ（バイアス補正後）の軸成分の積分 φ = ∫ s·ω_f dt で定義する（常に正方向に増える）。
クォータニオンから求めた相対回転角は 180° で折り返すため、積算にはジャイロ積分を使い、
姿勢制御へ戻す時点でクォータニオンとの整合を確認する。

| フェーズ | 入るとき | レート指令（3 軸） | 集合推力 T_c | 出るとき | 時間の目安 |
|---------|---------|-------------------|-------------|---------|-----------|
| P1 Boost | 実行条件成立 | 姿勢ループを通す通常制御（水平保持） | T_hi = `max_thrust_`（0.672 N） | t ≥ t_boost（0.15 s） | 0.15 s |
| P2 Spin | P1 終了 | 回転軸 = s·ω_flip（§7: α_cmd のランプで立ち上げ）、他 2 軸 = 0。**姿勢ループは通さない**（ACRO と同じ経路） | φ < φ_a: T_spin_hi ／ φ_a ≤ φ < φ_b: T_lo ／ φ ≥ φ_b: T_spin_hi（§5.3: 加速・減速窓は T_hi でなくトルク余裕を残す T_spin_hi） | 計画の減速開始点（指令が掃いた角 + ω_cmd²/(2·a_down) ≥ 2π、§5.7）。計測角が指令角の 0.5 倍未満なら回転が始まっていないとして打ち切り | 0.24 s（ロール） |
| P3 Brake | 計画の減速開始点 | 回転軸 = 0（§7: α_cmd のランプで減速。レート PID が減速トルクを出す）、他 2 軸 = 0 | T_spin_hi | **\|ω_f\| ≤ ω_h（300 °/s）（φ に関係なく）**、または φ ≥ 360°（`handoff_force_deg`）、または `brake_timeout_ms`（300 ms）。§10 参照 | 0.2 s（ロール） |
| P4 Recover | P3 終了 | 姿勢ループに戻す（roll = pitch = 0、yaw = 開始時の値。傾き誤差はクォータニオン由来で任意の姿勢から有効。§10） | 傾きで決める（§10: 水平近傍は T_hi、反転中は T_lo） | 傾き ≤ 20° かつ v_z ≥ 0、または t_recover ≥ 0.8 s | 0.2〜0.4 s |
| 完了 | P4 終了 | 通常モードの設定点（ALT/POS: 高度目標 = 開始時の高度、位置目標 = 現在位置。ACRO/STABILIZE: スティック） | 通常 | — | — |

角度のしきい値:

- φ_a = 60°（加速が終わり推力がまだ上向きの範囲を過ぎる角度）
- **（2026-10-02 改訂、§5.7）** 減速開始は計測角から先読みで決める方式（φ_brake = 360° − (ω_f²/(2·α_brake) + ω_f·t_lag)）をやめ、「計画」プロファイルにした: 指令が掃いた角 + ω_cmd²/(2·a_down) が 2π に達した時点で減速ランプを始める。面積がちょうど 360° になり、アクチュエータの遅れは波形を時間方向にずらすだけで回転量を変えない。以下の φ_b は、この計画上の減速開始角（360° − ω_cmd²/(2·a_down)）を指す
- φ_b = 計画の減速開始角 − 20°（減速の直前にトルク余裕を確保する）

推力の切り替えを角度で行う理由: 推力ベクトルの鉛直成分は cos φ に比例するため、
反転している間（90°〜270°）の推力は機体を下へ押す。加速（φ < φ_a）と減速（φ ≥ φ_b）に
必要なトルク余裕は T_c/4 と (0.168 − T_c/4) の小さい方で決まるので、その区間だけ T_hi にし、
惰性で回っている区間は T_lo まで下げて下向きの推力を減らす。

### 3.3 制御則（既存パイプラインの流用）

- P2/P3 のレート制御は既存のレート PID（`rate_roll_`/`rate_pitch_`/`rate_yaw_`）をそのまま使う。設定点だけを列生成器が与える。積分項は P2 開始時と P4 開始時にリセットする（減速時の巻き込みを防ぐ）
- P3 の減速はレート PID の飽和（`max_roll_pitch_torque_`）で行う。指令 0 と計測 ω_f の差が大きいので出力は上限に張り付き、最大トルクで減速する。姿勢角の計算には依存しない
- P4 の姿勢制御は既存の姿勢 PID。**（2026-10-02 改訂）** 当初は φ ≥ 290° まで待った（ピッチ回転で ZYX オイラー角が 270° 手前まで roll/yaw = 180° の枝にいるため。`to_euler()` の pitch は asin で ±90° に折り返す）。この待ちは、打ち切り後に Brake が永久に終わらない原因になった（§10）。現在は PID の測定値をオイラー角でなく重力方向の最短回転ベクトル（`FlipSequencer::levelError`、小さな傾きでオイラーと一致）にしたため、折り返しと特異点がなく、角度に関係なく姿勢ループへ渡せる（`handoff_min_deg` は廃止）
- 鉛直チャネル: P1〜P4 は `VerticalPhase::Airborne` のまま、集合推力を列生成器の値で上書きする（高度カスケードは休止）。完了時に高度目標を開始時の値に戻し、高度カスケードの積分項をリセットして再開する

### 3.5 打ち切りと安全

| 事象 | 処置 |
|------|------|
| P2 で `spin_timeout_ms` 以内に計画の減速開始点に達しない | P4 へ（水平化＋上昇） |
| \|ω\| > `gyro_abort_dps`（3 周期連続。IMU 飽和の保護） | P3 へ（即減速） |
| P3 で `brake_timeout_ms` 経過 / \|ω_f\| ≤ ω_h（φ 不問） | P4 へ（§10） |
| 衝撃検出（IMPACT 3 G） | 既存どおり即 DISARM（宙返り中も有効） |
| API `emergency` | 既存どおり即 DISARM |
| API `stop`/`land`、モードスイッチのエッジ、誘導目標 | **宙返り完了まで保留**し、完了後に適用（0.6 s 以内。途中で止める方が危険） |

| 角速度異常（GYRO_ANOMALY） | **マニューバ窓（P2 開始〜P4 終了 + 200 ms）の間は記録のみで無視**（§3.7） |

### 3.6 推定器の扱い

- 姿勢: ESKF のクォータニオン伝播（ジャイロ）はそのまま。加速度観測は適応 R と χ² 判定で自動的に重みが下がるため、宙返り中は実質ジャイロ積分になる。0.5 s 程度なら誤差は小さい（ジャイロバイアスは事前に収束している）。案 A の当初は「明示的な加速度観測の停止は入れない」としたが、**オリジナルとの比較（§6.4）を踏まえ、最終提案（§7）ではマニューバ窓の間は加速度観測による姿勢補正を明示的に止める**
- ToF: 反転中は天井までの距離を測るが、既存の傾き判定 `tof_tilt_threshold` = 0.70 rad（40°）で観測が棄却される（`eskf_core.hpp:84`, `eskf_core.cpp:534-537`）。追加実装は不要。SILS プラントは 90° 超で無効にするだけだが、ファーム側の 40° 判定が先に効く
- 光学フロー: 品質判定で棄却される（`eskf_core.cpp:733`）。傾きの明示判定は無い。Phase 2 で SILS のログで確認
- 気圧: 継続（50 Hz、`baro_innov_gate`）。反転中の気圧の変動は小さいと見込む（推測、実機ログで確認）
- 完了後: 位置目標を現在位置に取り直す（宙返り中の水平位置のずれは追わない）

**推定器が追従できるかの見積り（2026-09-16、オーナーの問いへの回答）**

| 要因 | 数値・根拠 |
|------|-----------|
| 1 周期の回転 | 1500 °/s × 2.5 ms = 3.75°/周期 |
| 積分方式 | `Quat::from_rotvec(gyro·dt)`（指数写像、`eskf_core.cpp:197`）。1 軸回転なら積分誤差ゼロ。レートが周期内で変わる分（ランプ中 ½·α·dt² ≈ 0.05°/周期）は加速と減速で相殺 |
| ジャイロ雑音 | 0.009655 rad/s/√Hz（`eskf_core.hpp:46`）× √0.5 s ≈ 0.4° |
| ジャイロ感度誤差 | 360° × 感度誤差。1 % なら 3.6° が復帰直後の姿勢残差になり、窓の終了後に加速度観測で消える（1 s 程度、推測）。バイアスは校正済みだが感度は未校正。最大の誤差源 |
| 加速度観測の誤補正 | 適応 R = R·(1 + k·\|a−g\|²)、k = 10（`eskf_core.hpp:126`。`detailed_design.md` の 50 はコードと食い違う → 文書修正）。反転中は \|a−g\| ≈ 1.5〜10 m/s² で R が 20〜1000 倍になり、姿勢共分散（≈ 1e-4 rad²）に対するゲインは 1e-4 以下。0.3 s 積み上げても 1° 未満。§7 の明示的な停止はこれを確定させるため |
| 制御への遅れ | ImuTask が予測 → ControlTask が同期起動（1 周期以内）。姿勢ループへ渡すのは減速後（≤ 300 °/s → 0.75°/周期）なので影響は小さい |
| 保険 | 列生成器が自前で積分した回転角と ESKF の相対回転角を切り替え時に照合し、20° 以上食い違えば ESKF の姿勢をジャイロ積分側に合わせる（測った値でのリセット。オリジナルの無条件リセットとは異なる） |
| ToF の絶対イノベーション判定 | `tof_innov_gate` = 0.5 m（`eskf_core.hpp:80`, `eskf_core.cpp:551-552`）。回転中に推定高度が真値から 0.5 m 以上ずれると復帰後も ToF が棄却され続ける。高度損失 0.3〜0.5 m は境界上 → **窓の終了時に ToF の再取り込みを保証する処置**（窓直後だけ判定を緩める、または最初の有効な ToF で高度を再初期化する）を Phase 2 に含め、SILS `api_flip` で「復帰後に ToF 観測が採用に戻る」ことを判定項目にする |
| v_z | 姿勢 5° のずれで推力 18 m/s² の 1.6 m/s² が水平に誤配分されるが、鉛直成分の誤差は cos 5° で 0.4 %。Recover の終了条件には十分。水平位置は 0.5 s で 0.1 m 程度ずれる |

結論: 姿勢は 400 Hz のジャイロ積分だけで 1° 未満の精度で 360° を追える。注意が要るのは高度側（ToF の再取り込み）で、これは判定項目として SILS で確認する。

### 3.7 フェイルセーフとの整合

角速度異常判定（800 °/s）は「墜落・衝突の検出」が目的であり、宙返りの回転はこれに該当しない。
INV-3（検出と判断の分離）に従い、**検出器（`ImuAnomalyDetector`）は変えず、判断側（`StateManager`）が
「状態 FLIP の間の GYRO_ANOMALY は墜落ではない」と扱う**（`handleAlert()` の状態分岐に FLIP を足すだけで、
側道の信号は要らない。§4 の改訂で `maneuver_active` は廃止）。衝撃判定（3 G）は FLIP 中も
有効のまま残す（ぶつかったときの停止手段）。代案（検出器のしきい値を FLIP 中だけ 1900 dps に上げる）は
検出器に「マニューバ」の概念を持ち込むので採らない。

Boost 中の加速度計のノルムは推力 1.85 G ＋ 回転中心からのずれによる遠心加速度（IMU が中心から 1 cm なら 0.7 G）で
3 G に近づく可能性がある。実機ログで確認し、必要なら窓内だけ衝撃しきい値を 4 G にする（§9）。

## 4. アーキテクチャへの組み込み

### 4.1 配置

**2026-09-16 改訂**: 当初案は「制御器内の時限オーバーライド（同定励振 `excite_active_` と同型）」で、StateManager には
`maneuver_active` という側道の信号でモードエッジの保留や GYRO_ANOMALY の無視をさせる構造だった。オーナーの問い
「突然モードが遷移するのは vehicle の方針と整合するか」を受けて見直した結果、これは (1) 規範表に状態として現れない、
(2) 制御器が事実上の状態を持つ（遷移の実行者は state_task のみ、`architecture.md:464`）、という 2 点で vehicle の方針と
半分しか整合しない。vehicle で遷移が「突然」でも整合する条件は、規範表にあること・onExit/onEnter で整えること・
制御器が単一パイプラインのままであること・state_task が遷移を実行することの 4 つであり、`requirements.md:52` の設計原則も
「TAKEOFF/LANDING は専用モード」「シーケンス（FLIP, AUTO_LAND 等）は将来拡張可能」と FLIP を専用シーケンス状態として想定している。
そこで **TAKEOFF/LANDING と同型の `FlightState::FLIP` を追加する**設計に改める。

| 要素 | 置き場所 | 役割 |
|------|---------|------|
| `FlightState::FLIP` | `sf_state/include/flight_state.hpp` | 専用シーケンス状態。`FLYING → FLIP`（要求 + 実行条件）→ `FLYING`（完了／打ち切り）。FLIP 中も `FlightMode`（ALT/POS 等）は保持（TAKEOFF と同じ） |
| `FlipSequencer` クラス | `firmware/vehicle/components/sf_controller_pid/flip_sequencer.{hpp,cpp}` | フェーズ進行、回転角の積算、レート設定点・集合推力・姿勢ループの要否を毎周期返す。`start(direction)`, `update(gyro, quat, height, v_z, dt)`, `abort()`, `status()`。実行条件 C2〜C8 の判定もここ（検出層） |
| `PidController::compute()` | 既存 | `ControllerCmd::Flip` を受けている間、列生成器の出力を設定点として既存のレート PID／姿勢 PID／ミキサーに流す。姿勢則は替えない（INV-1） |
| `ControllerCmd::Flip{dir}` / `FlipComplete` | `sf_core` | StateManager → 制御器への指示（`Takeoff` / `TakeoffComplete` と同じ経路）。打ち切りは制御器内で Recover へ進むので専用の動詞は持たない。IDLE_GROUND への遷移では既存の Reset が走る |
| `controller_status` 拡張 | `sf_types` | `flip_phase`、`flip_done`、`flip_result`（Ok / Rejected(reason) / Aborted(reason)）。`takeoff_reached` と同型。**遷移は制御器が行わず、state_task がこれを読んで `FLIP → FLYING` を実行する** |
| `ApiCmd::Flip{dir}` | `sf_types` | API → StateManager |
| `cmdFlip()` | `api_task.cpp` | 事前判定（command モード・FLYING）→ `ApiCmd::Flip` 発行 → **状態が FLIP を経て FLYING に戻るのを `waitUntil` で待つ**（`cmdTakeoff` が FLYING を待つのと同型。専用の完了カウンタは不要）→ `ok` / `error flip: <理由>`（理由は `flip_result`） |
| StateManager | `sf_state` | 規範表（§4.3）に従い `FLYING → FLIP` を判断し `ControllerCmd::Flip` を発行。FLIP 中の事象は表のとおり処理。onEnter / onExit で取り込みとリセット |
| state_task | `tasks/state_task.cpp` | `flip_done` の立ち上がりで `FLIP → FLYING` を実行。`CTRL_FLAG_FLIP` の立ち上がりで `ApiCmd::Flip` 相当の要求（Phase 3、実装済み・2026-09-18: `handleFlipButtonEdge()` が状態 FLYING・`controller_status.flip_ready` を確認し `determineFlipButtonDirection()`（スティック閾値超なら roll/pitch の符号、両軸未満なら `flip.button_default_direction`）で方向を決めて `requestFlipManeuver()`＝`StateManager::requestFlip()` を呼ぶ。API の `ApiCmd::Flip` 処理と同じ関数を共有） |
| 通知・テレメトリ | `sf_notify`, `sf_telemetry` | FLIP 状態の LED 色（オリジナルの橙 `0xFF9933` を踏襲）、テレメトリの状態値 |

onEnter（FLYING → FLIP）: 開始高度・ヨーの取り込み、レート PID 積分項リセット、推定器の加速度姿勢補正の停止（§7）、LED。
onExit（FLIP → FLYING）: 位置目標の取り直し、高度目標 = 取り込み値、高度・位置カスケードの積分項リセット、推定器の観測復帰と ToF 再取り込み、
`FlightMode` の初期化は通常のサブモード進入と同じ（スロットル再センターロックは ACRO/STABILIZE のときのみ）。

列生成器を制御器コンポーネントの中に置く理由: 400 Hz のジャイロ積算と、レート PID の積分項リセット・飽和挙動に密に結びつくため。
別コンポーネント化してトピック経由にすると 1 周期（2.5 ms）の遅れと状態の二重管理が生じる。状態そのものは StateManager が持ち、
列生成器は「FLIP 状態の中で何をするか」だけを持つ（TAKEOFF 状態と `VerticalPhase::TakeoffClimb` の関係と同じ）。
L1 アプリフック（`sf::app::controller()`）で制御器全体を差し替えた場合、Flip はその制御器の責務になる（文書に明記）。

### 4.2 不変条件（INV）との照合

| INV | 照合結果 |
|-----|---------|
| INV-1 単一パイプライン | 姿勢 PID・レート PID・ミキサーは変更しない。列生成器は **設定点の出所** を有限時間だけ切り替えるだけで、並列の姿勢則は作らない（ACRO が姿勢ループを通らないのと同じ経路）。鉛直チャネルの上書き（T_hi/T_lo）は「フェーズが変えてよいのは鉛直チャネル」の範囲内。`VerticalPhase` は増やさず、`Airborne` 内の一時上書きとする |

### 4.6 拡張性の検討（2026-09-16、オーナーの問い「別のモードを取り込む拡張性はあるか」への回答）

vehicle は旧版の状態遷移管理の曖昧さ（`Mode` / `Control_mode` / `Throttle_control_mode` / `Alt_flag` / `Flip_flag` が
重なり合い、優先順位が暗黙で、フラグが遷移を跨いで残る — オリジナルの Flip 不具合 §6.1 はすべてこれに由来）への
反省から、enum 状態 × 規範表（INV-4）、単一の遷移実行者、onExit/onEnter へのリセット集約、クラス A/B の境界条件、
検出と判断の分離（INV-3）、単一パイプライン（INV-1）を入れた。実測では TAKEOFF/LANDING を特別扱いする箇所は
firmware 全体で 16 箇所・4 ファイル（StateManager 8、state_task 5、離着陸 MGR 2、ImuTask 1）に集中しており、
**状態として足す限り拡張は局所的**である。当初案（制御器内オーバーライド）は旧版の `Flip_flag` の再来であり、
この構造を迂回する拡張だった。

Flip で露呈した不足は構造ではなく規則の明文化で、Phase 1 で `architecture.md` / `detailed_design.md` に書く:

| # | 規則 | Flip への適用 |

### 5.7 レートプロファイルの再調整（2026-10-02、修正計画のステップ 5）

候補を数値で比べて作り直した。掃引用の試験プログラムは `control/design/flip_plant_fit/flip_profile_sweep.py`、

### 6.4 優劣の判断

**オリジナルが優れている点**

1. **簡潔さと実績**: 40 行程度で実機の宙返りが成立している。時間駆動なので推定器の精度に依存せず、Madgwick の加速度補正が回転中に乱れても結果に影響しない
2. **レート指令の三角形プロファイル**: 角加速度 ≈ 141 rad/s² はトルク上限の 1/4 程度で、レート PID が線形範囲で追従できる。著者案のステップ指令（最大トルク）より制御器に優しく、実機調整済みのゲインがそのまま使える
3. **予備上昇の長さ**: 0.375 s × 1.2 倍で上昇速度 ≈ 0.7 m/s を付けてから回る。著者案の 0.1 s × 1.65 倍（≈ 0.64 m/s）と同程度だが、電流の立ち上がりが穏やかで電池電圧の低下が小さい（推測、§5.3 で確認）
4. **指令角 324° という実機合わせ**: 閉ループの追従遅れを係数 1 つで吸収している。著者案は同じことを角度計測で自動的に行うが、計測が正しいことが前提になる

**オリジナルが劣っている点**

1. **`ahrs_reset()` による水平宣言**: 実回転角を検証せずに姿勢を水平と定義し直すため、終了姿勢がずれた場合に角度ループが誤った姿勢を保持する。再収束は β = 0.1 の Madgwick に依存し、数秒単位（推測）
2. **実行条件が無い**: 低高度・低電圧・傾いた状態でも起動する。API から呼ぶ用途には使えない
3. **打ち切りの穴**: スロットル 10 % 未満での途中終了、OverG 2 G の誤検出の可能性、`Alt_flag` 残留時の推力上書き（副で一部解消）
4. **反転中の推力 1.0×（主）**: 下向きに押す分だけ高度損失が増える（副で 0.15× に改められている）
5. **ロール 1 方向固定・ラダー入力が生きる**: Tello 互換（4 方向、ヨー保持）にならない

**著者案が優れている点**: 回転角に基づく切り替え（電圧・質量・追従性の違いに自動で追従）、推定器の連続性と姿勢ループによる能動的な水平復帰、4 方向、実行条件、単一の鉛直チャネルによる高度制御との競合の設計上の排除、SILS で自動判定できる構造。

**著者案が劣っている点・危うい点**: (a) 回転中の ESKF が加速度観測で乱れると、オリジナルのリセットと同じ失敗（誤った基準への水平化）が、より予測しにくい形で起きる。§3.6 の「既存の適応 R に任せる」は不十分で、**マニューバ窓の間は加速度観測による姿勢補正を明示的に止める**べき（作者にも「着陸時 Madgwick Filter Off」の前例がある）。(b) ステップ状のレート指令は PID を飽和させ、積分の巻き込みと微分項の急変を招く。オリジナルの三角形（ランプ）を取り入れ、**角度で区切りつつ指令はランプにする**方が無理がない。(c) 状態・ステータス・規範表の追加で実装量が増える（SILS 判定と API 応答のためには避けられない）。

## 10. 実機初回試験の解析と構造修正（2026-10-02）

ログ `logs/flip_test1.sflog.zip`（1.46 m からの右ロール、`flip.enable` を有効にして試験）。

### 10.1 何が起きたか（数値）

| 時刻・量 | 値 |
|---------|----|
| Boost | 152 ms |
| Spin の指令 | 1500 °/s、ランプ 300 rad/s²。実際の立上げ ≈ 346 rad/s²、ジャイロは rate_ref に約 22 ms 遅れ、**計測 1909.5 °/s まで行き過ぎた**（BMI270 レンジ 2000 °/s、飽和はしていない） |
| ジャイロ打ち切り | 旧上限 `gyro_abort_dps` = 1800 °/s を超え、φ = 78.7° で `AbortedGyroLimit` → Brake |
| Brake | 減速 ≈ 443 rad/s²（トルク上限 7 mNm に張り付き）、回転は φ ≈ 207°（反転、傾き ≈ 155°）で停止 |
| Brake の出口 | 旧: (φ ≥ 290° かつ \|ω\| ≤ 300 °/s) または φ ≥ 350° のみ。時間切れなし。φ が 207° で止まると**永久に成立しない** → Brake に 0.33 s 留まり、推力 0.5·max（反転中は下向き）のまま衝突。Recover には一度も入らなかった |

### 10.2 原因

1. **Brake が終わらない**（構造欠陥、INV-2 違反: 有限時間でも単一の出口でもない）。φ ≥ 290° の条件は「Recover の姿勢誤差にオイラー角を使う」前提（§3.3）から来ていた。
2. **ジャイロ打ち切りが通常のオーバーシュートで作動した。** 1800 °/s は 2000 °/s のレンジに対して余裕を取りすぎ、1909 °/s の通常のオーバーシュートで切れた（飽和していないので打ち切る理由が無かった）。
3. **ホバー前提条件が操縦者に見えない。** FLIP ボタンの拒否はシリアルログのみで、飛行中は無音。

### 10.3 修正（構造のみ。スピン/減速ゲインは変えていない）

| 項目 | 内容 |
|------|------|
| Brake の出口 | \|ω\| ≤ `handoff_rate_dps`（φ 不問）/ φ ≥ `handoff_force_deg` / `brake_timeout_ms` の 3 つ。必ず終了する |
| Recover の姿勢誤差 | 重力方向の最短回転ベクトル（クォータニオン由来、任意の姿勢で有効）を既存の姿勢 PID の測定値にする。出力上限は FLIP 中 `recover_rate_limit_dps`（600 °/s） |
| Recover の出口 | 傾き ≤ `recover_boost_tilt_deg` かつ v_z ≥ 0、または `recover_timeout_ms`。打ち切り直後に v_z ≥ 0 だけで放さない |
| Recover の推力 | 水平近傍は増強、`angle_a_deg` まで T_spin_hi、以降は cos(tilt) に比例して縮め、反転で `thrust_lo_n` |
| Recover のヨー保持 | 傾き ≤ `recover_boost_tilt_deg` のときだけ（傾いた機体のオイラーヨーは無意味） |
| ジャイロ打ち切り | 1950 °/s、3 周期連続（IMU 保護）。作動時は Brake。継続は採らない（作動する状況では積算 φ と制動角の前提が崩れており、検証できるのはゼロ指令だけ） |
| ボタン UX | 拒否はエラー音＋ログ。一過性の NotSteady は `button_wait_ms`（1 s）保持して窓を待つ。CLI `status` に `flip` 行 |

### 10.4 Recover の推力方針を決めた SILS の試行

`flip_abort_recover` 系（`gyro_abort_dps=1000`、`brake_ramp_rps2=100` で反転 168° に止める）。

| 条件 | 結果 |
|------|------|
| 姿勢ループ出力上限 172 °/s（通常飛行のまま） | 回転が 171 °/s で止まらず進み、−4.8 m/s で床に衝突 |
| 上限 600 °/s、`thrust_lo_n` 0.03 N | 傾き 86° まで 0.16 s、そこでの落下 −3.4 m/s（h = 0.85 m）。それでも着地前に 0.2 m で水平化できず衝突 |
| 上限 600 °/s、0.2 N | 同じ傾き履歴（86° まで 0.16 s）、落下 −3.6 m/s（h = 0.83 m）。わずかに悪い |
| 上限 1500 °/s | 600 °/s と同一（姿勢の P 則 kp = 5 /s が支配的で、上限は効いていない） |

結論: (a) 姿勢ループの出力上限を上げないと遅すぎる。(b) 姿勢の立て直しは P 則（時定数 0.2 s）で決まりトルク余裕は支配的でないので、反転中は推力を縮めるほうが落下が遅い。(c) それでも約 1.3 m で反転した状態からの回復は、立て直し約 0.35 s と落下約 0.5 s の競争になり、高度が足りない。**自由落下中の反転は構造では救えない** — 回避は開始高度とスピンのオーバーシュート低減（後続のゲイン調整）で行う。

### 10.5 実行条件（C3/C4）の実測と判断

実機ログの 5.5〜15.7 s のホバー区間（操縦者が操作中。スティック中立が 0.5 s 以上続いたのは 0.81 s と 0.87 s の 2 区間のみ）:

| 量 | 全区間 p50 / p90 / p95 / p99 | スティック中立 0.5 s 以上（n = 669、400 Hz） |
|----|------------------------------|------------------------------------------------|
| \|v_z\| [m/s] | 0.37 / 0.83 / 1.31 / 1.72 | 0.17 / 0.57 / 0.64（max 0.83） |
| 水平速度 [m/s] | 0.21 / 0.42 / 0.48 / 0.54 | 0.23 / 0.32 / 0.33（max 0.38） |
| 高度 [m] | 1.07 / 1.52 / 1.61 / 1.64 | 1.03 / 1.23 / 1.27 |

境界 \|v_z\| ≤ 0.2 の違反は全区間の 70 %（スティック中立でも 67 %）、全条件成立は 17 %（最長 0.38 s）。**これは境界が厳しすぎる証拠ではない**: 操縦者が高度・スティックを動かし続けた区間で、v_z は実際に動いていた（高度 0.65〜1.6 m）。一方 SILS の定常ホバー（0.5 m、8〜17 s）は \|v_z\| p95 0.033、p99 0.12、max 0.14 m/s で、境界 0.2 に十分収まる。
**判断: 既定値は変えない。** 実機の「手を離したホバー」データが無く、境界の妥当性を裏付けも否定もできない。必要なのは 10 秒以上スティックを触らないホバーのログ（確認後に p95 + 余裕で見直す）。代わりに UX 側で対処した（ボタン保持 1 s、エラー音、`status` の `flip` 行）。

### 10.6 残る課題

- スピンの行き過ぎ（指令 1500 に対し計測 1909 °/s）は §5.7 で対処した（計画 360° プロファイルで計測ピーク 1615 °/s、フィット済みプラントの SILS）。実機での確認は §11 の再試験で行う。
- 1.3 m 付近で反転に打ち切られた場合は救えない（§10.4）。
- Recover の増強推力は傾き 20° 未満になってから（横に蹴り出さないため）。反転後の降下速度が大きいと v_z ≥ 0 まで 0.3 s 以上かかる（SILS `flip_abort_recover` 系で最低高度 0.26〜1.0 m）。

## 11. 実機再試験の手順（ステップ 5 のあと、未実施）

§5.7 の計画 360° プロファイルは、SILS の中でだけ裏付けた。プラントは実機ログ 1 本（ロール軸のみ）にフィットしたもので、ピッチ軸は暫定、
ホバー系の小信号の遅れは別。したがって再試験は**ロール右 1 回から**始め、結果を見てから次へ進む。

**準備と安全:**

| 項目 | 内容 |
|------|------|
| 場所・装備 | ネットを張った屋内、天井 ≥ 3 m。機体は開始高度 **1.5 m 以上**（計算上の高度低下は 0.2 m 前後、最悪でも 0.7 m 程度。ただし自由落下中の反転は救えない: §10.4）。操縦者は機体の真下に立たない |

(2) ロール右（API `flip r`、または FLIP ボタン + ロールスティック右）を **1 回だけ**。(3) 回復して FLYING に戻ったら着陸。左・ピッチは、(4) の判定を満たしてから 1 方向ずつ。

**ログで見るもの（新しい `flight_phase` / `flight_flags` ストリーム）と合格の目安:**

| ストリーム・量 | 期待（SILS のフィット済みプラント） | 外れたときの意味 |
