# 講習会でのペアリング取り違え対策（方式の比較と提案）

作成: 2026-09-11。**状態: 決定（2026-09-11 ユーザー確認）。実装中。**

状態: **実装中**（Phase 1〜2 完了、Phase 3〔文書・運用更新〕は進行中、実機での2組同時ペアリング検証は次回）。作成 2026-09-11、最終更新 2026-09-12。

**決定（2026-09-11）:** §3.1 の **W3（コントローラが受信した機体の MAC 下 4 桁を画面に一覧表示し、
利用者が複数候補から選んで確定する方式）のみを採用**する。ペアコード（W2）、近接自動選択（W1）、
Grove ケーブル（C1）、コントローラ CLI + `sf pair`（P1）は今回は見送る。W3 だけで講習会の運用は
実用上ほぼ問題なく成立する、との判断。

**電文は変更しない:** 現行のペアリング電文は機体の完全な MAC を含み、操縦電文は宛先機体の MAC
下 3 バイト（`drone_mac`）を含む。W3 に必要なのは (1) コントローラが「最初の 1 通」ではなく候補を
集めて画面で選ばせること、(2) 機体がペアリング中も「自分宛（`drone_mac` 一致）の操縦電文」だけを
相手候補にすること、の 2 点であり、§4.1 の電文 v2 は不要になった（§4 の実装設計を参照）。

発端: 講習会のように多人数が同じ部屋で同時にペアリングすると、隣のセットと取り違えて
意図しない組（クロスペアリング）になる。現行の唯一の対策は「1 組ずつ順番に、他は電源
OFF」という運用ルールで、参加者が同時に操作する講習では守りきれない。

方針の前提（ユーザー指示 2026-09-11）: 無線だけで解決する方式、有線で両機をつなぐ方式、
コントローラにも CLI を付けて双方 CLI でペアリングする方式、複数の方式を併存させる方式を
それぞれ検討する。

## 0. 要旨

| 観点 | 内容 |
|------|------|
| 取り違えの原因 | 機体は「ペアリング中に最初に届いた操縦電文の送信元」を、コントローラは「最初に受信した署名付きペアリング電文の送信元」を、それぞれ無条件に相手と確定する。電文には「StampFly である」ことを示す固定署名しか無く、「どの機体・どのコントローラか」を表す情報が無い。設計文書 `firmware/vehicle/docs/pairing_plan.md` の P4（未着手）に既知の弱点として明記済み |
| 根本対策の共通基盤 | どの方式でも最後は「コントローラが相手機体の MAC を知り、機体は自分宛（`drone_mac` 一致）の電文だけを受理する」形にする（**宛先指定ペアリング**）。ペアリング電文を v2 に拡張し、識別子（ペアコードまたは宛先 MAC）を載せる |
| 提案する組合せ | 層 1（既定・追加ハード不要）: コントローラの画面に受信した機体を一覧表示し、機体のラベル（MAC 下位 2 バイト）と照合して選ぶ。近接順（受信強度）に並べる。層 2（講習向け・確実）: コントローラに USB シリアル CLI を追加し、`sf pair` が PC 経由で両機に相手 MAC とチャンネルを書き込む。層 3（任意・後日）: Grove ケーブルで両機を直結して MAC を交換 |
| 効果 | 層 1 で「同時にペアリングモードに入っても取り違えない」を達成（相手は人が選ぶ）。層 2 で「無線に一切依存しない決定的な手順」を講習に提供 |
| 副次効果 | 事後の誤ペア検出（`sf pair status`、画面の MAC 照合）、公開ガイドへの注意書き追加、SILS の 2 組同時ペアリング試験 |

## 2. 問題の整理

取り違えは「誰が誰と組むか」を決める情報が電文にも操作にも無いことに尽きる。対策は
次の 2 つのどちらか（または両方）を与えることである。

1. **識別子**: 両機が共有する値（ペアコード、宛先 MAC）を電文に載せ、一致しない相手を
   受理しない。
2. **帯域外の経路**: 無線以外（画面での選択、USB、ケーブル）で相手を確定してから無線を
   使う。

どの方式を採っても、最終形は「コントローラが機体 MAC を知り、機体は自分宛だけを受理する
（宛先指定ペアリング）」に収束する。これを共通基盤として先に作り、その上に入力手段を
載せるのが最も手戻りが少ない。

## 3. 方式の比較

### 3.1 無線のみ

| 案 | 仕組み | 長所 | 短所・リスク | 実装規模 |
|----|-------|------|------------|---------|
| W1 近接選択（受信強度） | 両側で受信強度が最大かつ閾値以上（例: 機体をコントローラに接触させた距離）の相手だけを採用。候補が複数近接なら保留して LED で警告 | ハード・操作の追加なし。「近づけて押す」だけ | 隣席が数十 cm で同時にやると破綻。閾値が環境（筐体・電池・机の材質）に依存し、調整が要る。単独では決定的でない | 小（受信コールバックに `rx_ctrl->rssi` を通す、両ファーム） |
| W2 ペアコード（PIN） | 両機で同じ 1〜2 桁のコードを設定し、ペアリング電文と操縦電文に載せる。一致しない相手は無視 | 決定的。座席番号 = コードで運用しやすい。無線だけで完結 | 機体側のコード入力が不便（ボタン押し回数、または USB CLI `pair code N`）。電文の拡張（v2）が必要 | 中（電文 v2、両ファーム、コントローラの入力画面） |
| **W3 コントローラで候補を選ぶ（推奨・層 1）** | コントローラは受信した全ペアリング電文の MAC 下位 2 バイトを受信強度順に画面へ一覧表示し、利用者がスティックで選んで決定。以後は**その MAC 宛**に操縦電文を送る。機体はペアリング中も自分宛（`drone_mac` 一致）の電文だけを受理 | 決定的。追加ハード不要。機体側の操作不要。ラベル照合が手順に組み込まれる。既存の MAC 表示・ラベル運用と整合 | コントローラの画面 UI 実装。機体に MAC ラベルを貼る運用が前提（既にセット番号ラベルあり） | 中（コントローラ UI、機体側は受理条件の変更のみ） |
| W4 ボタン同時押し + 時間窓 | 両機でボタンを同時に押した 2 秒以内の相手だけを採用 | 操作が直感的 | 隣が同じ瞬間に押せば同じ問題。単独では不十分（W1 と組み合わせる前提） | 小 |
| W5 チャンネルで分ける | コントローラ側で先にチャンネルを固定し、走査を固定チャンネルだけにする | グループ数（3）まで分離できる | 同一チャンネル内の同時ペアには無効。1/6/11 の 3 グループが上限 | 小 |

### 3.2 有線（機体とコントローラを直結）

| 案 | 仕組み | 長所 | 短所・リスク | 実装規模 |
|----|-------|------|------------|---------|
| C1 Grove ケーブルで MAC 交換 | 両機の Grove を専用ケーブルでつなぎ、UART で互いの MAC とチャンネルを交換して保存。「挿す → LED 緑 → 抜く」 | 完全に決定的。PC 不要。講習で最も説明が易しい | 機体の Grove ピン配置・電源電圧が未確認、コントローラ側の Grove の有無も未確認。ケーブルの製作・配布。両ファームに UART 交換の実装。誤挿入対策 | 中〜大（ハード確認が先） |
| C2 物理接点（ポゴピン等） | 機体をコントローラに載せると接点で交換 | 手順が最も簡単 | 筐体の改造が要る。本計画では対象外 | 大 |

### 3.3 双方 CLI（PC が仲介）

| 案 | 仕組み | 長所 | 短所・リスク | 実装規模 |
|----|-------|------|------------|---------|
| **P1 コントローラに USB CLI を追加し `sf pair` で書き込む（推奨・層 2）** | コントローラに `controller>` コンソール（`mac`、`peer set <mac> <ch>`、`channel set N`、`peer status`）を実装。機体 CLI に `mac` と `peer set <mac>` を追加。`sf pair` が両機から MAC を読み、互いに書き込んで再起動。USB ポートが 1 つでも挿し替えを対話で誘導 | 無線に一切依存しない。講習は PC 前提なので手順が `sf` に統一される（既存方針）。`sf pair status` で誤ペアを機械的に検出できる | コントローラの USB は現在ゲームパッド（HID）専用で、CDC との同居（複合デバイス）の実装確認が要る。書き込み後の再起動と USB 抜き差しの手間 | 中（コントローラ側の CDC コンソール新設が主） |
| P2 機体の WiFi CLI 経由 | 機体の TCP CLI に `peer set` を追加 | 機体側は無線で済む | コントローラ側に対応する経路が無いので P1 が前提。単独では成立しない | 小（P1 の付属） |

### 3.4 併存

| 案 | 内容 | 評価 |
|----|------|------|
| **M1 = W3 + P1（推奨）** | 既定は W3（ハード不要、1 人で完結）。講習は P1（`sf pair`、決定的）。どちらも共通基盤（宛先指定ペアリング）の上に載る | 2 つの経路が独立しているので、片方が使えない状況（PC 無し／画面が見えない）でももう片方で組める |

## 4. 実装設計（決定版: W3 のみ）

### 4.1 機体側（firmware/vehicle）

| 項目 | 変更 |
|------|------|
| 受理条件 | ペアリング中（`PairingState::Pairing`）に届く操縦電文のうち、`drone_mac[0..2]` が自 MAC の下 3 バイトと一致するものだけを相手候補にする。一致しない電文（隣のコントローラが別の機体を選んだもの）は無視。成立後のフィルタ（相手 MAC 以外を破棄）は従来どおり |
| ペアリング電文 | 変更なし（500 ms ごとの一斉送信、内容は チャンネル + 自 MAC + 署名） |
| CLI `mac` | 新設。USB モニタ接続（`sf monitor`）で自 MAC を表示する。1 行目に完全な MAC（`XX:XX:XX:XX:XX:XX`）、2 行目に**ラベル用の下 4 桁**（例 `A1B2`）を出す |
| CLI `pair status` | 自 MAC（下 4 桁併記）と、バインド済みなら相手 MAC を表示する |
| 起動ログ | 起動時に自 MAC を 1 行出力する（モニタを開いたまま電源を入れれば分かる） |
| 設計文書 | `pairing_plan.md` の P4 に本方式を「実装済み」として記録。`espnow_tdma.yaml` の `multi_vehicle.collision_handling` を更新 |

### 4.2 コントローラ側（firmware/controller）

| 項目 | 変更 |
|------|------|
| 候補の収集 | ペアリングモードでチャンネル 1〜13 を従来どおり走査し、署名一致のペアリング電文を「最初の 1 通で確定」せず、送信元 MAC・チャンネル・受信強度を候補表（最大 8 件、同一 MAC は更新）に貯める。走査は利用者が決定するまで繰り返す |
| 画面 | LCD に候補を受信強度の強い順に表示。各行は「MAC 下 4 桁」と「CH」（受信強度は目安の記号）。行を選ぶとその行を反転表示。候補が 0 件のときは「Searching…」 |
| 操作 | スティック上下（または黄ボタン）で行を移動、画面押し込みボタンで確定。**候補が 1 件でも確定操作を要求する**（隣の機体しか見えていない場合の誤確定を防ぐ）。ペアリングモードからの離脱は電源再投入 |
| 確定後 | 選んだ MAC・チャンネルを SPIFFS（`peer_info.txt`）に保存し、その MAC をユニキャスト相手として登録。以後の操縦電文の `drone_mac` に選んだ MAC の下 3 バイトを入れる（既存の動作を確認して維持） |
| 成立の確認 | 機体からのテレメトリ（送信元 = 選んだ MAC）を受信した時点で成立と表示。一定時間（例 5 秒）受信できなければ「機体側がペアリングモードか確認」と表示して候補一覧に戻る |
| 受信強度 | ESP-NOW 受信コールバックの `rx_ctrl->rssi` を使う。取得できない IDF 版なら順序は受信順にし、強度表示を省く（機能は成立する） |

| 段階 | 内容 |
|------|------|
