# 講習会でのペアリング取り違え対策（方式の比較と提案）

作成: 2026-09-11。**状態: 提案（ユーザー未決定）**。§6 の決定事項に回答が付いた時点で「決定」に改める。

発端: 講習会のように多人数が同じ部屋で同時にペアリングすると、隣のセットと取り違えて
意図しない組（クロスペアリング）になる。現行の唯一の対策は「1 組ずつ順番に、他は電源
OFF」という運用ルールで、参加者が同時に操作する講習では守りきれない。

方針の前提（ユーザー指示 2026-09-11）: 無線だけで解決する方式、有線で両機をつなぐ方式、
コントローラにも CLI を付けて双方 CLI でペアリングする方式、複数の方式を併存させる方式を
それぞれ検討する。

## 0. 要旨

| 観点 | 内容 |
|------|------|
| 取り違えの原因 | 機体は「ペアリング中に最初に届いた操縦電文の送信元」を、コントローラは「最初に受信した署名付きペアリング電文の送信元」を、それぞれ無条件に相手と確定する。電文には「StampFly である」ことを示す固定署名しか無く、「どの機体・どのコントローラか」を表す情報が無い。設計文書 `firmware/vehicle/docs/pairing_plan.md` の P4（未着手）に既知の弱点として明記済み |
| 根本対策の共通基盤 | どの方式でも最後は「コントローラが相手機体の MAC を知り、機体は自分宛（`drone_mac` 一致）の電文だけを受理する」形にする（**宛先指定ペアリング**）。ペアリング電文を v2 に拡張し、識別子（ペアコードまたは宛先 MAC）を載せる |
| 提案する組合せ | 層 1（既定・追加ハード不要）: コントローラの画面に受信した機体を一覧表示し、機体のラベル（MAC 下位 2 バイト）と照合して選ぶ。近接順（受信強度）に並べる。層 2（講習向け・確実）: コントローラに USB シリアル CLI を追加し、`sf pair` が PC 経由で両機に相手 MAC とチャンネルを書き込む。層 3（任意・後日）: Grove ケーブルで両機を直結して MAC を交換 |
| 効果 | 層 1 で「同時にペアリングモードに入っても取り違えない」を達成（相手は人が選ぶ）。層 2 で「無線に一切依存しない決定的な手順」を講習に提供 |
| 副次効果 | 事後の誤ペア検出（`sf pair status`、画面の MAC 照合）、公開ガイドへの注意書き追加、SILS の 2 組同時ペアリング試験 |

## 1. 現状の事実（調査 2026-09-11）

### 1.1 電文と手順

| 項目 | 事実 | 出典 |
|------|------|------|
| ペアリング電文 | 11 バイト = チャンネル(1) + 機体 MAC(6) + 固定署名(4: AA 55 16 88)。PIN・乱数・機器 ID・受信強度の欄は無い。C++ 側には構造体すら無く定数のみ | `protocol/spec/messages.yaml:428-449`、`firmware/common/protocol/include/espnow_protocol.hpp:45-74` |
| 機体側 | 未ペア時は地上で自動的に、または本体ボタン 3 秒長押し／CLI `pair` でペアリングモード。500 ms ごとに上記電文を一斉送信。**ペアリング中に最初に届いた操縦電文の送信元 MAC を無条件に相手と確定**し NVS（`sf_pair/ctrl_mac`）に保存。成立後は相手以外の電文を破棄 | `firmware/vehicle/components/sf_comm/comm.cpp:459-497,518-561` |
| コントローラ側 | 電源投入時にボタン押下でペアリングモード。チャンネル 1〜13 を 200 ms ずつ順に切り替え、**署名が一致する最初のペアリング電文の MAC とチャンネルを無条件に採用**し SPIFFS（`peer_info.txt`）に保存 | `firmware/controller/components/espnow_tdma/espnow_tdma.c:129-152,496-546` |
| 選別の仕組み | 受信強度の比較、相手の選択画面、ボタン同時押し確認、PIN のいずれも無い | `pairing_plan.md:111-136` |
| 事後検出 | 自動検出は無い。コントローラ画面の MAC 下位 2 バイトと機体のセット番号ラベルを目視で照合するのみ。誤ペアは「本来の相手が操縦不能」という形で顕在化する | `docs/events/dxh2026/setup-loaner-pc.md:214` |
| チャンネル分散（1/6/11） | 成立後の電波干渉を減らす目的。ペアリング時はコントローラが全チャンネルを走査するため、取り違えの防止にはならない | `pairing_plan.md:127` |

### 1.3 文書の状態

公開ガイド（`README.md`、`docs/guides/controller.md`）には「同時に複数組をペアリングすると
取り違える」という注意が無い。注意は開発者向け（`operation_manual.md`、`pairing_plan.md`）と
講習運営用の内部文書（DXH2026）にしか無い。

## 2. 問題の整理

取り違えは「誰が誰と組むか」を決める情報が電文にも操作にも無いことに尽きる。対策は
次の 2 つのどちらか（または両方）を与えることである。

1. **識別子**: 両機が共有する値（ペアコード、宛先 MAC）を電文に載せ、一致しない相手を
   受理しない。
2. **帯域外の経路**: 無線以外（画面での選択、USB、ケーブル）で相手を確定してから無線を
   使う。

どの方式を採っても、最終形は「コントローラが機体 MAC を知り、機体は自分宛だけを受理する
（宛先指定ペアリング）」に収束する。これを共通基盤として先に作り、その上に入力手段を
載せるのが最も手戻りが少ない。

## 3. 方式の比較

### 3.1 無線のみ

| 案 | 仕組み | 長所 | 短所・リスク | 実装規模 |
|----|-------|------|------------|---------|
| W1 近接選択（受信強度） | 両側で受信強度が最大かつ閾値以上（例: 機体をコントローラに接触させた距離）の相手だけを採用。候補が複数近接なら保留して LED で警告 | ハード・操作の追加なし。「近づけて押す」だけ | 隣席が数十 cm で同時にやると破綻。閾値が環境（筐体・電池・机の材質）に依存し、調整が要る。単独では決定的でない | 小（受信コールバックに `rx_ctrl->rssi` を通す、両ファーム） |
| W2 ペアコード（PIN） | 両機で同じ 1〜2 桁のコードを設定し、ペアリング電文と操縦電文に載せる。一致しない相手は無視 | 決定的。座席番号 = コードで運用しやすい。無線だけで完結 | 機体側のコード入力が不便（ボタン押し回数、または USB CLI `pair code N`）。電文の拡張（v2）が必要 | 中（電文 v2、両ファーム、コントローラの入力画面） |
| **W3 コントローラで候補を選ぶ（推奨・層 1）** | コントローラは受信した全ペアリング電文の MAC 下位 2 バイトを受信強度順に画面へ一覧表示し、利用者がスティックで選んで決定。以後は**その MAC 宛**に操縦電文を送る。機体はペアリング中も自分宛（`drone_mac` 一致）の電文だけを受理 | 決定的。追加ハード不要。機体側の操作不要。ラベル照合が手順に組み込まれる。既存の MAC 表示・ラベル運用と整合 | コントローラの画面 UI 実装。機体に MAC ラベルを貼る運用が前提（既にセット番号ラベルあり） | 中（コントローラ UI、機体側は受理条件の変更のみ） |
| W4 ボタン同時押し + 時間窓 | 両機でボタンを同時に押した 2 秒以内の相手だけを採用 | 操作が直感的 | 隣が同じ瞬間に押せば同じ問題。単独では不十分（W1 と組み合わせる前提） | 小 |
| W5 チャンネルで分ける | コントローラ側で先にチャンネルを固定し、走査を固定チャンネルだけにする | グループ数（3）まで分離できる | 同一チャンネル内の同時ペアには無効。1/6/11 の 3 グループが上限 | 小 |

### 3.2 有線（機体とコントローラを直結）

| 案 | 仕組み | 長所 | 短所・リスク | 実装規模 |
|----|-------|------|------------|---------|
| C1 Grove ケーブルで MAC 交換 | 両機の Grove を専用ケーブルでつなぎ、UART で互いの MAC とチャンネルを交換して保存。「挿す → LED 緑 → 抜く」 | 完全に決定的。PC 不要。講習で最も説明が易しい | 機体の Grove ピン配置・電源電圧が未確認、コントローラ側の Grove の有無も未確認。ケーブルの製作・配布。両ファームに UART 交換の実装。誤挿入対策 | 中〜大（ハード確認が先） |
| C2 物理接点（ポゴピン等） | 機体をコントローラに載せると接点で交換 | 手順が最も簡単 | 筐体の改造が要る。本計画では対象外 | 大 |

### 3.3 双方 CLI（PC が仲介）

| 案 | 仕組み | 長所 | 短所・リスク | 実装規模 |
|----|-------|------|------------|---------|
| **P1 コントローラに USB CLI を追加し `sf pair` で書き込む（推奨・層 2）** | コントローラに `controller>` コンソール（`mac`、`peer set <mac> <ch>`、`channel set N`、`peer status`）を実装。機体 CLI に `mac` と `peer set <mac>` を追加。`sf pair` が両機から MAC を読み、互いに書き込んで再起動。USB ポートが 1 つでも挿し替えを対話で誘導 | 無線に一切依存しない。講習は PC 前提なので手順が `sf` に統一される（既存方針）。`sf pair status` で誤ペアを機械的に検出できる | コントローラの USB は現在ゲームパッド（HID）専用で、CDC との同居（複合デバイス）の実装確認が要る。書き込み後の再起動と USB 抜き差しの手間 | 中（コントローラ側の CDC コンソール新設が主） |
| P2 機体の WiFi CLI 経由 | 機体の TCP CLI に `peer set` を追加 | 機体側は無線で済む | コントローラ側に対応する経路が無いので P1 が前提。単独では成立しない | 小（P1 の付属） |

### 3.4 併存

| 案 | 内容 | 評価 |
|----|------|------|
| **M1 = W3 + P1（推奨）** | 既定は W3（ハード不要、1 人で完結）。講習は P1（`sf pair`、決定的）。どちらも共通基盤（宛先指定ペアリング）の上に載る | 2 つの経路が独立しているので、片方が使えない状況（PC 無し／画面が見えない）でももう片方で組める |
| M2 = M1 + W1 | W3 の一覧を受信強度順にするので、事実上 W1 を含む。閾値による自動選択はしない（保留の誤動作を避ける） | 推奨に含める |
| M3 = M1 + C1 | Grove の実態確認後に追加 | 後日判断 |
| M4 = W2 のみ | 電文にペアコードを載せる案だけで済ませる | 機体側の入力が不便で講習向きでない。W3 に劣る |

## 4. 提案する設計

### 4.1 共通基盤: 宛先指定ペアリング（電文 v2）

| 項目 | 変更 |
|------|------|
| ペアリング電文 v2 | 現行 11 バイトの署名の後に `version`(1)、`pair_code`(1、未使用時 0)、`controller_mac`(6、コントローラが送る場合) を追加。旧版は署名の後が無いので長さで判別し、当面は両方受理する |
| 機体の受理条件 | ペアリング中も操縦電文の `drone_mac[3]` が自 MAC 下位 3 バイトと一致するものだけを相手候補にする（成立後のフィルタと同じ条件をペアリング中にも適用）。これだけで「隣のコントローラに拾われる」経路が閉じる |
| コントローラの受理条件 | 「最初の 1 通」ではなく、受信した候補を集めて利用者（W3）または PC（P1）が指定した MAC に対してだけ操縦電文を送る |
| 仕様の正本 | `protocol/spec/messages.yaml` と `espnow_tdma.yaml` の状態機械を実装（機体 3 状態）に合わせて改訂し、`multi_vehicle.collision_handling: "Not currently implemented"` を更新する |

### 4.2 層 1: コントローラの候補一覧（W3）

1. ペアリングモードに入るとコントローラは全チャンネルを走査し、受信した機体 MAC・チャンネル・受信強度を最大 8 件まで保持する（3 秒間）。
2. LCD に「CH  MAC下位2B  強度」を受信強度順に表示。スティック上下で選択、画面ボタンで決定。1 件しか無く強度が十分なら 1 秒後に自動決定（単機運用の手間を増やさない）。
3. 決定した MAC 宛にのみ操縦電文を送り、機体からのテレメトリ（相手 MAC 一致）で成立を確認して保存。
4. 機体のラベルに MAC 下位 2 バイトを印字（現行のセット番号ラベルに併記）。

### 4.3 層 2: `sf pair`（P1）

1. コントローラに USB CDC コンソールを追加（TinyUSB の複合デバイスで HID と同居。切替が必要なら「電源投入時に黄ボタン押下で CLI モード」とする）。コマンド: `mac`、`peer status`、`peer set <mac> <ch>`、`peer clear`、`channel set N`、`reboot`。
2. 機体 CLI に `mac`、`peer set <mac>`、`peer clear` を追加（既存の `pair status` は維持）。
3. `sf pair`（新設）: 接続中の USB シリアルを自動判別し、機体とコントローラの両方が見えれば MAC を相互に書き込む。片方ずつしか挿せない PC では「機体を挿してください → 読み取り → コントローラを挿してください → 書き込み」と対話で誘導。最後に `sf pair status` で両側の相手 MAC が一致することを検証して表示。
4. `sf pair channel N`: 両機のチャンネルを同時に設定（1/6/11 分散の手順を 1 コマンドにする）。

### 4.4 検証

| 段階 | 内容 |
|------|------|
| SILS | 仮想コントローラ 2 台・機体 2 台を同時にペアリングモードに入れ、v2 では取り違えが起きない（旧版では起きる）ことを再現する試験を追加 |
| 実機（ベンチ） | 2 組を 30 cm 以内で同時にペアリング。W3 で正しい組になること、P1 で無線を切った状態でも組めること |
| 講習リハーサル | 10 組同時。手順書どおりに 5 分以内に全組が成立し、誤ペアがゼロ |

## 7. 未確認事項

- コントローラ側 Grove 端子の有無、機体側 Grove のピン配置と電圧（機体仕様書で「要確認」のまま）。

- ESP-NOW 受信コールバックの受信強度が両ファームの IDF 版で取得できるか（IDF 5 系では `esp_now_recv_info_t.rx_ctrl->rssi`）。
- コントローラ LCD の解像度と、一覧 8 件を読める文字サイズ。
