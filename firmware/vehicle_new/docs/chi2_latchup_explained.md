# 読み物版：ESKF の χ²（カイ二乗）ラッチアップ — 「信じすぎ」が招いた限界安定の破綻

> この文書は技術ノート [`chi2_latchup_finding.md`](chi2_latchup_finding.md) の**平易な読み物版**です。
> 「ドローンがなぜ位置を保てずに流れて行ったのか」「その真因をどう突き止めたのか」「なぜ
> 1行の変更で直ったのか」を、探偵小説のように順を追って説明します。
> 対象: 制御・ハードウェアは分かるが、この推定器の中身は初めて読む人。

---

## 0. この話のどこが面白いか

- **症状はとても不気味だった**。位置保持（POSITION_HOLD）モードで、ある時はピタッと止まり、
  ある時は 7m も流れて行く。違いは推力わずか **0.1%**、あるいは重力定数の **0.0035%**。
  連続的にじわっと悪くなるのではなく、**ある一線を越えた瞬間に挙動が不連続に発散する**現象だった。
- **最初の見立ては2回とも外れた**。「推定が数百度ズレて固着している」も「加速度の大きさで
  見分ければいい」も、計測したら違った。
- **真因は拍子抜けするほど単純**だった。そして直し方は**たった1つの数字**を変えるだけ。
- 教訓がきれいに出た：**勘で議論せず、測れ**。

---

## 1. 舞台設定：ドローンはどうやって「自分の傾き」を知るか

ドローンが姿勢（ロール・ピッチ）を保つには、まず「自分が今どれだけ傾いているか」を
**推定**しなければならない。使うセンサは2つ：

| センサ | 測るもの | 長所 | 短所 |
|--------|---------|------|------|
| **ジャイロ** | 角速度（回転の速さ） | 速い・滑らか | 積分するとドリフトする（少しずつズレが溜まる） |
| **加速度計** | 比力（重力＋運動加速度） | 重力で「下」が分かる＝絶対の基準 | 運動加速度が混ざる・振動でノイジー |

静止していれば、加速度計は**重力だけ**を測る。重力は必ず真下を向くので、
「加速度計が感じる下向き」と「機体の下向き」のズレ＝傾きが分かる。

そこで両者を**いいとこ取り**する。これが**状態推定器（ESKF＝誤差状態カルマンフィルタ）**の仕事：

```
   ジャイロ（速いがドリフトする）
        │  積分して姿勢を「予測」
        ▼
   ┌─────────────┐    加速度計（重力で下が分かる）
   │  姿勢の推定値  │ ◀── で定期的に「補正」
   └─────────────┘
```

ジャイロでなめらかに姿勢を進め、加速度計（重力）で時々ドリフトを引き戻す。
**この「引き戻し（補正）」が効かなくなると、姿勢はジャイロのドリフトに乗って流れていく。**
今回の事件の核心はここにある。

---

## 2. 問題：位置保持が「綱渡り」だった

毎軸の POSITION_HOLD / STABILIZE を SIL（ソフトウェア上の飛行試験）で回すと、
**限界安定**だった。つまり「かろうじて保っている」状態。

| 与えた違い | 横方向のドリフト | 結果 |
|-----------|----------------|------|
| 基準 | 1.08 m | OK |
| 推力 −0.1% | 0.92 m | OK |
| 推力 **+0.1%** | **7.40 m** | 発散（飛んで行く） |
| 重力 9.81→9.80665（**0.0035%**） | att 誤差 2.3°→**6.7°** | 発散 |

ほんの少しの違いで結果が**質的に**変わる。これは「パラメータを少しずつ動かすと性能が
少しずつ変わる」普通の感度ではない。**閾値を跨いだ瞬間に一気に発散する「臨界」的な破綻**である。
（以下、この「閾値を境に不連続に発散する境目」を **臨界** と呼ぶ。）

> 制御屋の直感：限界安定の系は、ループのどこかに「ギリギリで成立している補正」があり、
> それが何かのきっかけで成立しなくなると一気に崩れる。今回その「ギリギリの補正」が
> **加速度計による姿勢の引き戻し**だった。

---

## 3. 門番の登場：χ²（カイ二乗）ゲートとは何か

加速度計の補正には落とし穴がある。**マニューバ中は運動加速度が混ざる**ので、
加速度計が指す「下」は本当の下ではない（重力＋横加速度の合成方向）。これを鵜呑みにすると
「水平なのに傾いている」と誤判定して姿勢を壊す。

そこで**門番**を置く。補正を取り込む前に「この加速度の読みは信用できるか？」を検査する。
これが **χ²（カイ二乗）ゲート**：

- まず**イノベーション**を計算する。イノベーション＝「実際の測定値」と「推定からの予測値」の差。
  「どれだけ予想外だったか」。
- そのイノベーションが、**統計的に見てどれくらい『驚き』か**を数値 `d²`（マハラノビス距離の二乗）
  にする。`d²` が大きいほど「予想外＝怪しい外れ値」。
- `d²` がしきい値（例: 7.8）を超えたら、その読みを**まるごと捨てる**（補正しない）。

```
   加速度の読み ─→ イノベーション計算 ─→ d²（驚き度）
                                          │
                              d² > 7.8 ?  ├── はい → 捨てる（補正しない）
                                          └── いいえ → 採用（姿勢を補正）
```

考え方は妥当だ。「予想外すぎる読みは運動加速度に汚染されているから無視しよう」。
**問題は『どれくらいで驚くか』の基準だった。**

---

## 4. 驚きの基準は「どれだけ信じているか」で決まる

ここがこの事件の急所。`d²`（驚き度）は、次の式の感覚で決まる：

```
              （測定と予測の差）²
   d²  ≈  ────────────────────────
            （測定をどれだけ疑うか）
```

分母の「測定をどれだけ疑うか」が、推定器に教える**観測ノイズ `R`** だ。

- `R` を**大きく**設定（＝「加速度計はノイジーだと思え」）→ 多少の差は「想定内」→ `d²` 小さい → 採用。
- `R` を**小さく**設定（＝「加速度計はとても正確だと信じる」）→ ちょっとの差でも「ありえない！」
  → `d²` 爆発 → 棄却。

今回、この `R` が **`accel_att_noise = 0.06`**（`R = 0.06² = 0.0036`）と設定されていた。
**「加速度計は誤差 0.06 m/s² しかない超精密センサだ」**と推定器に教えていたわけだ。

ところが現実には、飛行中の加速度計のイノベーションは **1〜2 m/s²** ある（後で計測する）。
モデル化していない運動加速度・振動・α-βトラッカの残差などが乗る。
**1 m/s² の差は「σ=0.06」の世界では約 17σ** ＝「天文学的にありえない」レベル。

> つまり門番は、**「このセンサは絶対に間違えない」と信じ込んでいた**ため、現実の普通の
> ばらつきを全部「ありえない外れ値」と判定して叩き落としていた。**信じすぎが過剰な棄却を生む。**

---

## 5. 何が起きていたか（ラッチアップの実態）

マニューバ中、`d²` が常にしきい値を越え、**加速度の補正の約66%が棄却**されていた。
（しかも「悪い時だけ」ではなく、**ちゃんと飛べている時も66%棄却**していた。残り34%の
わずかな補正で綱渡り的に姿勢を保っていた。）

補正がほとんど効かないと、姿勢は**ジャイロ積分だけ**で進む → ドリフトが溜まる →
推定姿勢が真の姿勢から数度ズレる → そのズレた姿勢で位置制御するから、機体が
だんだん傾いて → **横に流れていく（7.4m）**。

この臨界の正体はこう：基準では34%の補正でギリギリ保てていたが、推力を 0.1% 足すと捕捉
マニューバがほんの少し激しくなり、棄却が一押し増えて補正が**収支割れ** → ドリフトが
止まらなくなって発散する。**ギリギリの綱渡りだから、わずかな一押しで落ちる。**

---

## 6. 探偵編：勘で2回外し、計測で当てる

### 外した仮説①：「推定が数百度ズレて固着している」

最初の見立ては「一度姿勢が大きくズレると、正しい重力の読みすら門番が外れ値扱いで弾き、
**回復補正を門番自身が拒否して永久に固着する**（＝ラッチアップ）」だった。

確かめるため、**この破綻を確実に再現する環境**を用意した（`SIL_EMU_BATTERY=off` で電池電圧の
ゆらぎという“偶然の救済”を切り、`pos_yaw` を走らせると必ず 7.4m 流れる）。そして
`updateAccelAttitude` の中身を時系列でログした。

結果は予想と違った：

```
  推定ロール/ピッチ = −2〜−8°   ← 数百度ではない！ ほぼ水平のまま
  ‖a‖−g（重力からのズレ） ≈ 0.01〜0.35  ← 加速度の大きさは重力とほぼ同じ
  |イノベーション| = 1〜3 m/s²   ← 普通の大きさ
  d² = 44〜996                  ← なのに驚き度だけ桁違いに大きい
```

推定は数百度もズレていない（せいぜい数度）。**`d²` が大きいのはズレのせいではなく、
分母の `R` が小さすぎるせいだった**。普通のイノベーション(1〜2)を 0.06 の物差しで測るから
17σ になって `d²` が爆発していただけ。「永久固着ラッチ」ではなく「**慢性的な過剰棄却**」。

### 外した仮説②：「加速度の大きさで本物の重力を見分ければいい」

次に「ラッチ中は加速度の大きさ ‖a‖ が重力 g に近い（測定は正しい重力）はずだから、
‖a‖≈g なら門を開いて補正を採れば回復するのでは」と考え、実装して掃引した。

結果は**逆効果**（バンドを広げると姿勢誤差が 202° に爆発）。ヨー中心のマニューバでは
運動加速度で汚染されている時も ‖a‖ が g に近いままになり、**大きさでは本物と汚染を
見分けられなかった**。仮説②も棄却。

### 計測が示した真因

2回の空振りの後、上の時系列ログが答えを指していた：
**`R`（加速度計をどれだけ信じるか）が現実離れして小さい。** 直すべきは門番の閾値でも
判別ロジックでもなく、**信頼度の設定そのもの**だった。

> 教訓：「数百度ラッチ」「ノルムで判別」という**もっともらしい物語は2回とも外れた**。
> d²・イノベーション・R を時系列で**測った**瞬間に真因が見えた。
> （CLAUDE.md の原則「制御/推定のパラメータ変更は数値で裏付けてから」がそのまま効いた。）

## 7. 改善：信頼度を現実に合わせる

`accel_att_noise` を **0.06 → 0.8 m/s²** にした（`R = 0.0036 → 0.64`）。
意味は「加速度計の姿勢観測には、運動加速度込みで 0.8 m/s² 程度の不確かさがある」と
**現実的に**推定器へ伝えること。これは元々コードの構造体に書いてあった既定値 2.0
（“ホバー時の振動ノイズに相当”）に近い側の値で、掃引で 0.8〜1.0 が安定だった。

掃引データ（`pos_yaw`、破綻を再現した環境）：

| accel_att_noise | 棄却率 | 姿勢誤差 att_rmse | 判定 |
|-----------------|--------|------------------|------|
| 0.06（元） | 71% | 8.84° | 発散 |
| 0.3 | 7% | 4.88° | 臨界の縁 |
| **0.8** | **~0%** | **1.13°** | **安定** |
| 1.0 | ~0% | 1.19° | 安定 |

棄却率が 71%→ほぼ 0% に落ち、姿勢誤差が 8.84°→1.13°（健全値 2〜3°より**良い**）。
門番を弱めたのではなく、**門番に正しい物差しを渡した**ので、普通の読みは「想定内」として
採用され、本当の外れ値（大きく外れた読み）だけが弾かれるようになった。

---

## 8. 結果：臨界が消え、副産物も解禁

- **臨界の解消**：電池電圧のゆらぎという“偶然の救済”を切った最悪条件でも、毎軸 POS_HOLD が
  全て安定（att_rmse 0.5〜1.1°）。もう推力 0.1% や重力 0.0035% では発散しない。
- **退行なし**：11 シナリオ・物理真値テスト（hover_smoke）・現実ノイズ（N1）・旧ファーム・
  実機ビルド、すべて合格。
- **解禁できた2つ**：
  - **重力定数の統一**（9.81→9.80665）。臨界があった頃はこの 0.0035% で発散したが、今は素通り。
  - **スティックのデッドバンド 0.05**（中央の不感帯）。同じく以前は破綻させたが、今は通る。
- 直したのは実質**コードの数字1つ**（`accel_att_noise`）。

---

## 9. この話の教訓（3点）

1. **限界安定は臨界（不連続な破綻）を生む。** ギリギリで成立している補正は、わずかな摂動で
   一気に破綻する。今回の臨界は、加速度補正が66%棄却の綱渡りだったこと。
2. **「信じすぎ」は危険。** 観測ノイズ `R` を実際より小さく設定すると、χ²（外れ値）ゲートが
   過敏になり、現実の普通のばらつきを全部「外れ値」として捨ててしまう。R は**現実のばらつきに
   合わせる**。
3. **勘でなく計測。** もっともらしい仮説は外れた。中の量（イノベーション・d²・R）を時系列で
   見える化したら真因は一発だった。推定器のデバッグは「中を測る」に尽きる。

## 付録：自分で再現・観察する手順

```bash
source setup_env.sh
sf sil build

# 破綻を再現（電池電圧のゆらぎを切る）— 元の値 0.06 では pos_yaw が 7.4m 流れる
SIL_EMU_BATTERY=off SIL_EMU_ACCEL_ATT=0.06 sf sil scenario simulator/sil/scenarios/pos_yaw.scn --target vehicle_new

# 直った値 0.8 では安定（att_rmse ~1.1°）
SIL_EMU_BATTERY=off SIL_EMU_ACCEL_ATT=0.8  sf sil scenario simulator/sil/scenarios/pos_yaw.scn --target vehicle_new

# 中の量を観察（d²・棄却率は emu の console.log に出る）
grep "chi2:" simulator/sil/viz/out_scn_pos_yaw/console.log | tail
```

掃引用の環境変数（再ビルド不要、`emu_main.cpp`）：
`SIL_EMU_ACCEL_ATT`（R の基準）・`SIL_EMU_CHI2_GATE`（門番の閾値）・`SIL_EMU_KADAPT`（適応Rの強さ）・
`SIL_EMU_BATTERY=off`（破綻を再現）。

技術的な詳細・棄却した代替案の記録は [`chi2_latchup_finding.md`](chi2_latchup_finding.md) を参照。
